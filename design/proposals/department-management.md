# 基层部门管理与生产协作

性质：部门管理实施设计与研究依据。用户目标、原方案取舍和实施前审查分别保留；现行规则归[社会系统](../systems/social_system.md#当前部门目标与运输合同)与[宗门生活](../systems/sect_life.md#已接入的生产合同)，阶段状态只归[主计划](../../docs/plans/foundation-priorities.md#基层部门管理与生产协作)，实测与限制归[BASELINE](../../docs/status/baseline.md#部门管理与生产协作)。后文的实施前缺口不是当前仍缺失的断言。

## 已确认的方向

- 首先做好一个基层厨房部门：有负责人、设施、人员、库存和上级任务。管事是实际NPC，玩家担任职位时可用面板办理相同范围的管理；后续战斗、探险部门不在本轮展开。
- 部门工作通过面板和管理命令发布、受理与分配，日常管理不再要求到告示案张贴、读榜、签领、回报，也不要求当面协商每次正常上工。
- 管理者可准确查看授权范围内的库存、生产和工作状态，系统自动统计实际履行，不制作人工盘点、报工或账实误差玩法。个人探索、关系、私有背包与内心仍不因管理身份全部公开。
- 工作台使用有限容量的容器库存，生产从台内选料；成功出品前不消耗原料。**暂停保留工时，明确取消整批清零工时，两者均不消耗原料、不生成成品。** 实际花过的时间和身体精力不倒流。
- 部门成员的组织劳动受部门及工作配置限制；同部门内可有重叠工作组，同一人可承担多种工作。技能/速度排优、复杂排班与高优强制抢断后置。
- 上级目标可以按游戏日给定产量，完成实际生产后自动核销；具体数量可配置。产量、现存库存、在途物品和交付分别成立。
- 管事能配置每台设施允许生产的内容、员工工作范围，向其他部门提出原料供应需求；仍需真实物资和到场运输。
- 玩家可担任从掌门到底层杂役以及自定义身份；面板按真实职责、可组合管理能力与作用范围适配，不以头衔名称或厨房专属分支鉴权。个人工作与管理权限分别表达，管理策略可有实际负责人而不以其唯一身份垄断全部权限。

“固定资产”在面板上拆为设施资产与人员配置，人物不是可转移库存。ERP/OA是管理体验类比，本方案借用部门、生产目标、工作分配与供料的清晰边界，不预建财务、薪资、审批流、通用BPM或现实企业后台。

正常厨房的目标流程：

```mermaid
flowchart LR
    A[上级生产目标] --> B[管事配置灶台与人员工作范围]
    B --> C[缺料时向供应部门请求]
    C --> D[供应受理并真实送达]
    D --> E[搬运者按配方补到台内]
    E --> F[工匠占工位加工]
    F --> G[完成才耗料并出品]
    G --> H[实际产量自动核销目标]
    G --> I[成品由搬运者归仓]
```

图中是职责与物料关系，不是要求管事每锅亲自调度；已有原料时可直接补台。目标暂停/日界、人员生活需要或空间不足分别按下文规则接续。

配方/设施/开局部门配置沿现有Godot Resource编译为只读定义；任职、批次、库存与目标保存运行事实。命令、恢复和观察继续沿原Runner/Frame/存档链，不引入ERP服务、数据库、运行时模型或另一套调度后端。

## 部门、工作组与资源范围

下列记录设计边界；实际代码沿原owner拆分规则，不按每行建立新系统、类或数据库表。现行字段与生命周期以源码及主题规则为准。

| 事实 | 最小责任与边界 |
|---|---|
| 宗门组织 | 原有成员及财产归属主体；物品organization不改写成部门编号 |
| 部门 | 组织内有单一上级的管理单元，保存名称、上级引用与负责人任职关联；校验同组织、无环。首个消费者是厨房 |
| 人员工作配置 | 引用真实人物、部门及允许的工作类型/设施范围；不复制技能、身体、移动或人物忙碌状态 |
| 工作组 | 部门内的分工集合；成员可重叠，可引用共用设施。首版不做任意矩阵汇报和跨部门抢人 |
| 设施管辖 | 每件设施有明确主管部门，工作组可以共享使用；共享引用不改变物权，不重复计资产/库存 |
| 生产目标与分配 | 由原事项owner扩展；目标规定结果，分配规定哪个组/设施范围承担多少，不复制第二份完成进度 |
| 生产配置与当前批次 | 设施配置允许配方和补料规则；process只保存正在加工的一批、原料承诺、劳动及任务归属 |
| 数量/容量预约与运输过程 | Institutions保存运单，Objects通过相关回调派生可用数量/空间，引用来源、去向、物料权属、数量及责任范围，跨取货与投递；World/P5只引用过程身份执行，原库存仍只有一份 |

部门表示管理关系，不等同于地图矩形。首版用真实设施/人员引用限定工作；地点是否可达仍由空间系统判断。厨房员工不能因为同属一个宗门就自动领取其他厨房的组织任务，跨部门组织劳动需明确调派/供料约定，本轮不自动发生。吃饭、睡觉、求学和安全活动继续使用原生活/自主框架。

例如同一搬运者同时属于厨房一组、二组：两个组可提供候选工作，但该人物仍只有原ActionGate与一个当前互斥过程。员工数/可用人力按真实人物ID去重；共享仓库库存按容器ID去重。部门继承的只是已授权管理范围，不把别人私产和整个宗门公库自动开放给所有员工。

工作配置、管理权限和物品用途许可分别判断：工作配置决定自主组织劳动可以挑哪些工作，不凭空授物权；职位决定可改哪些配置、查看哪些管理信息；取用仍核对象与物料的真实许可。保留有意授予上级管理者的全组织权限，不将它误判成漏洞而统一收回；普通成员原有吃饭/休养资格也不随部门调整删除。

## 目标、分配与实际结果

上级向部门下达生产目标，管事将目标分配给组或允许的工作台。宏观目标不绑定唯一工位；具体批次才绑定一台设施和实际操作者。新增的部门目标/分配沿原Institutions事项生命周期扩展，不能同时运行两套可互相结清的订单账。

建议首版同时支持可配置的一次目标与按游戏日重复目标，物理生产仍沿同一个process。生产配置可列多个允许配方；选取尚未满足且可行的工作，不借此提前引入技能排优、复杂权重和全局最优排程。

- 开工前核“实际已产＋有效在制/已承诺批次”的覆盖量，避免多台同时各自承诺整个目标。父目标分配额度也只能被合法占用一次。
- 完成时，由原`World.commit_activity`交接真实产物结果，核目标/分配/批次身份；组与部门按同一结果归因，汇总不把组产量与部门产量再次相加。
- 同一人跨组、换人接手、手动合法生产与读档接续均不能重复核销。未关联该目标的私人烹饪不自动冒充部门履职。
- 正式累计进度保存在原事项owner，界面与个人目标引用；不能靠重扫有界活动日志重算历史，加载也不重放产物与奖励。
- 生产统计按真实产出量；目标完成判定为达到要求。配方一批3份、目标100时，允许必要的最后一批使实际为102，面板如实显示；不制造半份配方，也不因已被在制覆盖而继续开新批。

建议组的分配数只表达父目标中的名义份额，不另发一份附加目标；已完成/在制是该份额的执行状态，不能再与完整分配额相加扣父额。改分配只移动尚未承诺的剩余部分，不暗改已开批归属；开新批同时核父目标与该分配的覆盖量。整批舍入可能让50份分配实际产51份，这是同一真实产出的上下级归因，不再把51加回父级一次。父额已达标时不为凑齐各组名义数继续超产。取消一批释放其在制覆盖，换人接手不新增覆盖。

具体准入为父级`已产+在制 < 目标`且该分配`已产+在制 < 分配数`；原owner在同次开批承诺中增加该批实际预计产量。提交时将同一份在制覆盖改成实际结果，取消则撤在制；不能先减目标剩余、再加WIP造成双扣。不同配方有副产物时，每个目标只按其指定物品/计量规则核销，副产物仍是真实库存，不当成另一份主产量。

分配的名义额度在关闭后仍保留已履行/在制所占部分；不能将“关闭”解释为释放完整额度再派一次。例如A/B各50，A产51后关闭，A不产生可再派的50份；B仍沿原父目标准入。一次移动的名义余量最多为`max(0, 分配数-实际-在制)`，有关记录随父单一起有界归档。实现时覆盖A已产30/在制3、将A/B调为36/64，以及A产51关闭后再增C等反例；允许整批舍入不等于强制所有状态永远满足“actual+名义配额之和≤目标”。

建议日周期使用已有环境游戏日（当前`Environment.DAY_MS=1200000`），不使用现实日期。每个周期实例有稳定身份，暂停/存读不重发当日任务。旧期未完显示欠额/逾期，停止再开旧期新批并结束无继续用途的未取补料需求，不静默把欠额叠加到新期；已开批保留原任务归属，晚完成算原单逾期履行。当天真实生产统计按实际完成时刻归日，与某单的按期履行分别展示。首版不自动堆积无限历史或无限欠单：无在制/在途引用的旧单按原有界历史方法闭合压缩，有活动引用的记录不能先淘汰。

目标暂停/撤销与取消实物批次不是同一个命令：建议暂停或撤销目标先停止开新批，既有批次仍可完成；需停止某锅时另行暂停或取消整批。撤销后形成的真实产物仍记录来源和实际产量，不把已撤销目标重新激活，也不把旧锅算到新期。具体按钮写清影响，不能一个“取消”同时悄悄销工时、退物、改订单。

## 工作台：同一库存，完成时转换

工作台仍是具体灶台/工坊设施，同时具有有限储物与生产能力。普通箱与灶台共享容器规则，各自保留收纳/工艺与交互约束。默认生产不再隐式从工匠背包扣料；兼职工匠要自取也通过同一取货、运输、放台过程。

1. 开工从台内真实库存选择合法原料，绑定当前批次的数量预约；原物留在库存，不能被另一批或普通取物重复使用，也不复制成第二份在制库存。
2. 操作者到实际工位后累计劳动，一台同一时刻只有一批，一批的人工阶段只有一名操作者。离岗释放人物/操作位，当前批次、已做工时与原料承诺保留；其他有能力且有范围权限的人可接手。
3. 明确取消整批清除该批工时和原料/输出空间承诺，原料仍在台内，绝不“生成一份退款”。取消不发生产实践或产量。
4. 最终提交核原料、设施、权限、目标归属和容量；同一事务消耗原料、产生真实成品，再核销目标。原完成产物不会因后来取消订单而倒回原料。
5. 已有无人静置仍按到期时刻运行，释放劳动者但保留同台唯一批次。建议区分自然离岗与明确暂停批次：无人静置不因操作者吃饭而中止；明确暂停保存当前阶段和剩余静置时间，继续后接续。取消/暂停要使旧到期凭据失效，不能取消后旧回调再产一次；最终产出仍核该阶段要求的操作或人工收取。

加工槽和工匠作业位的排他不等于封锁整台所有取放：搬运者仍可在不占用工匠位置的合法服务点操作未锁物料/成品。明确暂停保留的原料锁在面板标明，持续停产由有权者继续或取消处理，不用任意超时自动丢弃工时。取消当前批次也不等于关闭生产目标；若目标和配方仍有效，后续可以重新开批，按钮须说明这一影响。

暂停正在人工加工的批次时，先按当前时刻结算这段真实劳动，再释放操作绑定；取消则确保原run的interrupt/到期清理不能回写已删除批次或重新生成一次产物。首次开工费用、阶段和实践等原消费者同步核，不只改process字段后宣称可取消。

容量沿当前物品数量单位计算，不把它改成地图格数。设U为实际占用、I/O为本批输入/输出数量、R为其他有效入库承诺：开工核`U + R + max(0, O-I) <= 容量`，只为本批保留正的净增空间；完成核`U-I+O+R <= 容量`并在同次提交撤去本批净增预约，不能把它再扣一遍。容量3中2粮1水→3饭必须合法；1料→3成品需额外预约2。其他物品仍实际占空间，不能依赖未来必会消耗的物品提前腾位。转化还须预检合法物权组/批次容纳约束，再一次提交，失败不先扣输入。

补料按当前生产需求的每种原料缺口，扣除实有可用量和有效在途量；不能让一种原料塞满小工作台。成品未搬走时真实占用容量，缺空间显示停产原因。更换后续配方不默改当前批次；旧原料不消失，可合法运回仓。工匠操作位与搬运取放位复用原按operation配置的作业几何，仍检查身体/目的地占用。

首版自动备料只为当前要开的一批，不为已在制的下一锅提前发补料任务，也不把整日目标摊成无限台面预约。**备料时就要为已选配方的净增输出留下空间**：容量3、1料→3成品的空台只应备1料，不能先塞2料再因缺出品空间开不了工。配方每项缺口、真实余量、有效在途及净增余量共同限制备料；台面成品或自由余料阻塞时先解释/清运，不假定未来消耗必会腾位。

仓箱过滤沿实际物品目录字段配置，供给规则限定公共组织用途或指定工作台/工作组；公共供给不等于任何人可私取。工作台可接收缺口内原料、合法退料及真实成品，不能因为有storage能力被所有搬运者当成普通归仓箱。配方调整后不再需要的自由原料标为可清运，预约中的原料先按原批次/运输生命周期处理，不能直接删物。普通取放与自动搬运都核同一预约/容量合同，不能通过手动put绕过已保留空间、通过take拿走已锁输入。

公共原料送达工作台时可按合法公物保管交接结清原运输责任；加工公物由部门生产权限准入，不强行为台内原料伪造“操作者已经个人领用”。私人寄存物不自动转公、不与其他所有者材料无条件合批；携带途中的受托用途继续核权。

## 管事、员工和供应部门怎样行动

管事接到上级目标，使用自己的部门权限设置分配、工作配置和供料需求。玩家通过面板提交这些管理命令；NPC通过同一规则采用配置策略。管理命令校验实际操作者、任职范围、引用版本与会话，不执行走到告示案的身体动作，也不取消人物正在进行的合法动作。

管事维护目标与分工，员工在该分工允许的就绪工作中认领具体批次/运输。无需管事每次亲自挑选每个取放动作，也不让全知后台绕过其工作配置给所有人派活。既定职责的普通工作不再逐餐重新协商；能力不足、暂时忙碌、生活急需和安全中断仍按原框架处理。负责人暂时缺席不抹除有效计划，已有授权工作继续；自动继任和复杂人事制度后置。

首版NPC管理策略只消费相关目标/库存/人员配置变化：在允许的设施/配方中分配未覆盖目标、维护一份有效补料需求、将办不到的事标为受阻。员工选择和现场准入仍检查真实本领；本轮不按烹饪等级/速度给人排优，也不静默改掉玩家配置。谁任该职谁行使管理命令，玩家任职时没有隐藏NPC管事同时反复覆盖；管理日志/面板显示最近一次实质分配或请求及其结果，不为展示“忙碌”安排走案动作。

跨部门供料首版采用一个明确来源部门与目的部门的请求：

`提出需求 → 供应方受理数量/来源 → 有效在途承诺 → 实际送达 → 部分或全部结清`

建议默认由供应方安排所属搬运者送到约定的接收容器，接收权限仅覆盖该请求，厨房不因此得到供应部门全库取物权。部门内部再按自己的工作配置把原料送上工作台。没有可用供应量时显示受阻，不能把提出请求当成已经供货。多个请求竞争同一物料，沿同一数量预约口核对。

首个供方直接用正常开局的真实粮仓/供料设施、人员和任职装配一个最小仓储供应部门，先完成厨房—仓储的闭环，不同时扩完整农业管理。供应方须真实受理并派自己的可用搬运者；玩家管厨房时它也能由NPC受理，不能只做一个发出后永远无人处理的按钮。

数量按未受理、受理待发、在途、实收等互斥阶段迁移；“受理总量”如包含在途/实收，就只能作为汇总显示，不能再次相加扣需求。实收进入接收容器库存后也不再算一份在途。未受理请求可防止同源需求重复提出，但不算已获保证或当前可用物料；供应请求受理不保证具体库存；搬运者认领运单时才预约真实源货和目的空间。

供料请求归原Institutions事项owner，引用物资owner的有效预约/运输身份，不另保一套可独立消费的锁料账。将一份受理量交搬运者时，对同一预约绑定或分割出互斥运输份额，不能先按供应承诺锁一次、又按运单锁同一份两次。取货提交把来源预约转为人物实际保管与目的容量承诺，投递再结清，界面数量按这些真实阶段派生。

既有`entrustments`仍表达公物由谁为哪件事保管；新运输通过同一身份关联它，不另造一份公物责任。当前`_mandate`会按人/组织/用途/来源合并，尚无去向/运输身份；迁移时须能区分同源不同去向，不把两单混成可随意挪用的包。`AgencyPlanner._returns/_retains`已有当前目的保留判断，但须扩为识别真实活跃运输，不能仅因take已结束、临时改去吃饭便把合法在途当无用途余料退回；失效后仍沿合法退还/交接收尾。这是新合同的集成要求，不宣称当前已有已复现的退料缺陷。

受理20份不要求接收箱一次容下20份：受理仅接下需求，每趟按源真实可用量、搬运能力与目的余量预约；没有目的空间就不盲取。接收箱满、被拆或规则更改使原约定不可继续时，未取部分暂停/撤销并释放不再有效的锁定，已在途部分另行交接/退回；不通过虚拟收货清掉堵塞。

关联同一个需求来源去重/修订，不每次看见缺料就再发一份。受阻任务等待相关补货、容量/许可变化或已知复查到期；拒绝不触发立即重发同单。取消未取货部分释放承诺；已取货物不销毁，后续交付、退回或保留待办有明确责任。完成供应按真实接收计数，生产、承诺供应和搬同一堆货不能互相冒充。

## 面板与管理信息

| 页面 | 应看到的真实信息与可执行操作 |
|---|---|
| 概览 | 本部门/上级、负责人、目标进度、当日产量、在制、供料缺口与主要受阻原因 |
| 设施与库存 | 厨房/仓库/灶台引用、主管与使用范围；台/箱真实物品、可用/已约/在途分别显示；收纳与供给去向设置 |
| 人员与工作组 | 人物、允许工作、负责设施与组关系；当前工作/休养/等待原因；分配、移组、撤销工作配置 |
| 生产 | 上级目标、允许的配方和工作台/组分配；当前批次进度、暂停、继续、明确取消整批 |
| 供料请求 | 对端部门、请求/受理/在途/实收数量、接收地点与受阻状态；提出、受理或撤回本人有权办理的部分 |

“现存”只汇总本范围内真实容器，合法可用量再扣他人权属与预约；携带物显示为在途，不能既留在来源库存又算进目的可用量。组共享资产只是一份引用，统计去重。有管理权不等于有消费/转让所有物资的权力。

管理读模型是授权范围内准确的运行信息，发布可标世界时刻/修订，短暂显示延迟不需要玩法中的盘点。它独立于个人Knowledge，不把全宗门真实快照塞进每次operation_actor或给所有NPC灌实时记忆；只对相关工作提供必要目标/位置和条件。未管理的部门、私人背包与内心不随面板开放。

## 成本与恢复合同

沿当前调用入口控制新增倍率，以下是设计时的访问合同；现行查询与剩余成本见架构及BASELINE，不预报收益：

| 入口与频率 | 当前/新增风险 | 采用的范围与维护 |
|---|---|---|
| `Livelihood.prepare_plan → _self_view → World.operation_actor → Institutions.access_view`；每次个人规划，实际操作还会再读 | 现Access扫全部任职/服务；若再附全部门工作/库存，任何生活动作也会承担这份成本 | 相关C02按本人任职/服务关联读取；部门选活另取窄范围输入，同阶段复用，授权改变失效；不把部门报表加进通用actor |
| 原`AgencyInstitutions.duty/service`与后续部门选活；每个确实需要新决定的员工 | 每人遍历所有部门/设施，或一个变化通知全部员工再各扫一遍 | 人物工作配置关联本部门/组的就绪候选，相关变化合并唤醒；工作被占/取消/材料到达时更新对应候选，等待和公平沿原调度 |
| `World.begin_operation → Facilities/ServicePositions.occupants`；每次候选作业点 | 现单点扫全部身体/目的地，调用点数和请求率相乘 | 相关C03沿原身体/导航/预约事实派生局部查询；覆盖片内移动与同批准入，搬运取放不能绕检查 |
| `Production.start/commit`与`Objects.transfer`；实际开批、收尾、取放 | 每次物料变化重算所有工作台，或物量锁/供料承诺各扫一遍世界 | 按设施当前批次、该容器物品权属批和关联预约读写；相关配方需求/来源失效，不每步全表valid。开批受影响的现有actions扫描一并核实，不能复制到新循环 |
| `Runner._publish`部门订阅；管理页打开且相关版本变化 | 每渲染帧/每个NPC重建全宗门报告；共享资产重复汇总 | 原物写入口失效相关部门汇总，按打开范围构造脱离页；上级汇总沿真实管辖关系去重，读取r项仍付O(r)，关闭停止专用发布 |

- 任职、部门人员/设施、组关联和活动订单沿原owner维护可重建的按人/部门/设施索引；新增或撤职、拆除、换组与读档须同步维护。部门树向有关上级汇总，不全宗门广播。
- 原物变化从原库存写入口产生相关失效；源料、容量、配方、目标与员工可用性变化只使相关工作待评估。通知合并到相关就绪集合，一个新活不令所有成员各自完整规划一次；已有合法过程继续。已知日界/静置/重试到期进入原调度。后台只作脱离候选，owner采用时复核，世界不等待所有管事规划完成。
- 单个工人只读所属工作范围和有关来源，不做每人×全部部门×全部工作台匹配；运输候选不遍历全世界仓库。面板只对打开的部门/页发布变化摘要，大列表可分页，关闭后停止专用订阅；汇总不是第二库存账。
- 现有C02个人权限读全任职/服务、C03每候选作业点扫全身体是本轮相关前置接缝，须在增加请求量时一并收窄并验证。C01完整调度整改另沿原计划，不默认本次管理方案已完成它。
- 清理以预约所归过程为准：人物死亡/换职释放其身体执行与不能继续的运输绑定，不顺手取消公共工作台批次；仍合法的批次可换人接续，暂停仍保原料绑定。拆台或明确取消整批才结束该批并释放其预约，真实原料按原物权回收。撤权/供给规则变化核受影响的未取承诺和继续资格，已取货物需交付、退回或交接，不能只释放责任让它失踪。跨take/put的运输承诺不能随take结束消失；管理员可看清哪一过程仍占量/空间。
- 管理/生产/运输事实保存一次，索引和汇总恢复重建；恢复先验证独立候选，不从历史回执再发任务、物料或产量。实施采用format33与新默认文件，保留旧32档和受保护旧包，不承诺全格式迁移链。

规模反例固定一个厨房及相关人/物，只增加无关部门、任职和远处身体，检查单次管理/选活/取放的访问量及维护量；再核真实完成量、积压与等待。允许结果本来有r项时付出O(r)，不能只报FPS、队列内耗时或把无关组织扫表藏在helper里。

## 实施出口

分步施工与每步可观察成果归[主计划](../../docs/plans/foundation-priorities.md#基层部门管理与生产协作)。每步沿正常main与原开局装配接真实消费者，最终交付可管理的厨房，不另做独立部门demo。管理先接一个厨房与最小真实供应方；生产底层更换时同步迁移所有受影响方法/准入/恢复消费者，原自取自制方法改走取→放台→做，不留旧物料后端。最终把原四院厨事/送餐配置用同机制迁移，日常主链不保留“旧告示模式”开关；其他社会渠道按真实消费者另行保留或清理。

首轮应能观察：上级任务进入部门面板，管事配置两组共用搬运者，设置灶台生产，缺料发供应请求，供料实送后各台生产并自动结算，成品入仓；共享人不双排，暂停可换人续作，取消不耗料。对应反例还包括最后一份料/最后一格容量争用、在途改设置/拆台/死亡、缺成品搬运、跨日和中途存读。技能优先级、真实报工/盘点、财务薪酬、复杂继任和战斗探险部门不纳入本轮。
