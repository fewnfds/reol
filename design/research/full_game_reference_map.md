# 完整游戏的参考取舍与素材路线

> 核查日期：2026-11-02。用途：支持完整游戏的长期方案；这里的 Reol 方案是设计推导，不是已实现功能。
> 当前能玩什么仍以 [BASELINE](../../docs/BASELINE.md) 和 [实际代码核对](../../docs/DEMO-REFACTOR-REPORT.md) 为准。
> 本轮阅读公开资料，没有逐一试玩参考游戏，没有复制其代码或素材，没有安装新依赖或下载素材包。

## 研究结论

最适合 Reol 的组合，是以同一个世界中的人物、物资、组织和信息为基础，分别提供个人冒险、组织经营和区域竞争的操作入口。不能把每款参考游戏的全部机制相加，再要求每套机制都达到原作深度。

优先借鉴的七件事：人物日常能够自行推进；工作与交易有真实需求；权力落实到人和职位；失败能够继续；修炼改变行动能力与社会处境；战争会改变补给、人员和地盘；玩家能从线索理解世界怎样变成现在这样。

“世界自主运行”也不等于把全世界所有单位逐帧运行。参考作品证明了多种取舍可以形成可信体验；它们的商店宣传不能证明某种具体算法、数据结构或远区精度。Reol 必须为自己的连续性、公平性和性能建立测试。

### 哪些看似相近，实际必须分开

1. **叙事导演、脚本状态变化与自主行动。** 三者都可以存在，但用途不同。导演选择已有事件的呈现或有限外部压力；脚本负责特定场景；人物规则负责做决定、动身和付出代价。不得让导演伪造“某个具名 NPC 已经行动过”的历史。
2. **角色扮演与殖民管理。** 视角可以切换，权利不能凭视角产生。普通弟子只能请求或认领工作；管事凭任命分配值役；掌门能定政策，但成员是否执行仍取决于组织约束和处境。
3. **战略数量与具体资源。** 可以按队伍统计远区口粮、伤员和工时，但再次入场时应能还原为合法的已有人员、货物和状态。抽象不应提供免费补给。
4. **修仙跨度与日常跨度。** 如果境界、寿命和闭关有几十年尺度，就需要人口、继任、传承和记录的规则。不能只把钟拨快，同时把其他人冻住；也不能要求玩家重复操作几十年的三餐。
5. **真实因果与复杂 UI。** “库房断药，因为进山路被封”比堆出几十条派系百分比更能解释局势。账目、通行、报价和交谈呈现人能够获知的事实，调试器再显示完整数值。

### 三种组合是否成立的检查场景

| 场景 | 需要连起来的系统 | 玩家至少应有的替代选择 |
|---|---|---|
| 宗门缺粮，河湾愿意卖，但路上有人劫掠 | 生产、市场、钱、物流、风险、政治 | 买粮自运、雇人、请求护送、谈通行、改种植或缩减征调 |
| 突破前夕师父受伤，药材也是自己的突破材料 | 修炼、关系、伤病、承诺、稀缺资源 | 救师延期、找替代药、借贷求助、交易传承、选择自保并承受后果 |
| 玩家远游后返回，旧友已不当权 | 时间、职位、知识、凭据、继任、组织执行 | 查公账、拜访旧友、找担保、协商旧承诺、另谋门路；不能靠一条声望值自动恢复福利 |

这些都是 Reol 推荐验收情境；本研究没有声称现有 Demo 已完成其中所有环节。

### 可复核的引入记录

沿用 [Assets 约定](../../assets/README.md) 和 [第三方声明](../../THIRD_PARTY_NOTICES.md)，按实际需要创建清单，不先堆空目录。每个包至少记录：

| 字段 | 必须回答的问题 |
|---|---|
| 名称、作者、原始来源 URL | 具体文件是谁创作、从哪里取得？不能只写“GitHub”或“OGA” |
| 发布版/commit、下载日期、原包 SHA-256 | 后续能否找到同一份内容、发现被替换？无版本号用哈希固定 |
| 许可证标识、版本、原文、所选许可路径 | 多重许可究竟采用哪一个？源码与素材是否分别授权？ |
| 文件/部件范围、署名文本 | 实际用了哪些，不只记录素材包封面？LPC 要到部件级 |
| 修改记录与产物映射 | 哪些经过改色、裁剪、拼装、子集化、重录或转换？ |
| 技术规格 | 视角、原生尺寸、帧表、透明度、锚点、滤镜、色盘、音频格式、内存预算 |
| 审核状态 | 候选、占位、已核许可、已引擎验证、可发布；未完成核查不得标“可发布” |

发布包提供可发现的 Credits 和必要许可文本；从清单生成署名，抽查不漏项。不自动宣称改变游戏自身许可证；项目自身发布许可尚待发布阶段确定。

## 代码生成表现：能延续现有工作的路线

本轮实际读过的现有表现代码：

- [PawnVisuals](../../scripts/entities/pawn_visuals.gd)：衣襟、发髻、地影和选中标记，共用绘制人物；不拥有身体状态。
- [FacilityVisuals](../../scripts/world/facility_visuals.gd)：井、药圃、山门与建筑的几何剪影。
- [TerrainVisuals](../../scripts/world/terrain_visuals.gd)：稳定变体和小型地表图集。
- [ReolUITheme](../../scripts/ui/reol_ui_theme.gd)：颜色、文字、按钮和面板的共用样式。

推荐延续它们的职责：纯模拟只输出状态；表现层决定衣着、动作、材质和特效。换精灵不得改库存、人物 ID、格子占用、命中判定或权限。

| 对象 | 玩法开发期 | 正式美术期 |
|---|---|---|
| 人物 | 共用剪影＋衣色/头饰/工具表示角色；需要时先补走、做事、受伤、施法的清楚状态 | 先锁一个人物的正交比例、四向与动画，再做同族服饰和装备层；不一次生成海量互不一致人物 |
| 建筑 | 明确占地、入口、工位和仓储容量；轮廓区分功能；施工/损坏/停工能辨认 | 按村舍、宗门、工坊等模块做屋顶/墙/门/招牌，保证同类尺度、遮挡和切换规则 |
| 地形 | 稳定色块、边界、道路和可走提示；渲染不反过来决定规则 | 制作少量拼接正确的地形族，检验连续3×3拼接、海量重复和远近缩放 |
| 战斗/修炼 | 瞄准范围、前摇、命中、闪避、受伤、突破结果可读；廉价几何特效足够 | 补冲击、剑气、符箓、灵气和少量音色；先保证拥挤战斗可辨认，再添粒子 |
| UI/地图 | 信息组织、键鼠焦点、缩放与因果说明随玩法实现 | 统一图标、字体、装饰和音效；文字保持代码/本地化资源，不烘焙进图 |

代码生成图集时固定种子和生成参数；能离线烘焙的族图集优先烘焙，不每帧重画复杂纹理。生成器不复制商业图片或轮廓。AI 栅格图可作为后期绘制工具，但也必须经过尺寸、透明度、拼接、逐帧稳定性和实际游戏比例检查；记录工具、日期和人工修改，不把“生成成功”当素材验收通过。

### “玩法先行”的实际门槛

玩法阶段仍需要可读的画面、基础反馈和可用 UI，否则无法判断操作本身是否好玩；这里推后的是大量正式资产和装饰，而不是推后所有体验验证。

正式美术批量生产前需要同时满足：

1. 个人生计、修炼冒险、据点生产经营三条循环都能用占位资产完成，并出现真实取舍。
2. 离场推进、失败恢复、跨层事务和完整存读通过各自验收，换图不会掩盖规则缺陷。
3. 画布、逻辑格尺寸、人物/门/道路比例、相机缩放范围、碰撞与锚点约定稳定；地图规则不依赖最终贴图分辨率。
4. 选一张“宗门院落＋几个人物＋工作＋小战斗”的样板图，在实际尺寸和缩放下验证色盘、剪影、昼夜、迷雾和信息密度。
5. 样板的许可、资源预算、中文字体和音频路径能进入发布包；再按清单分族替换占位。

采用“样板→小族→场景验证→批量”的顺序。若公开包难以统一国风方向，就以现有代码剪影和自制模块为主，开放素材补充合适的基础图块/音效；不为利用某个免费包改变整个玩法或视角。
