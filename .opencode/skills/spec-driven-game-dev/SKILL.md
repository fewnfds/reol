# Spec-Driven 游戏开发

## 为什么

AI 最危险的时刻，是你说“帮我做个殖民地系统”，它立刻开始写 2000 行。
**先把“做什么/为什么/怎么验收”写清楚，再写代码。**

---

## 何时用

- 新系统/新功能。
- 改动跨 2 个以上系统。
- 需求模糊、有多种做法。
- 你发现 AI 在猜/过度设计/范围膨胀。
- 需要给未来的自己/别人留记录。

**不适用**：改错别字、调一个数值、修一个明确的编译错误。

---

## 工作流（8 步）

### 1. Intake（1 段话）

用 3–6 行写清楚：

```
目标：
玩家体验：
约束：
非目标：
验收：
```

如果写不出来，说明还没想清楚；先讨论。

### 2. Clarify（最多 3 个问题）

只问真正阻塞的；每个问题给推荐默认值。

```
1) 单角色还是可指挥殖民者？默认：单角色 + 可指挥。
2) 实时还是回合？默认：实时 + 空格暂停。
3) 失败是否读档？默认：失败推进故事，不强制读档。
```

其余按 `docs/GAME-BRIEF.md` 默认值推进，记录到 ADR。

### 3. Design Note（设计笔记）

复制 `references/design-note.md`，写：
- 玩家体验/决策/反馈。
- 规则/优先级/边界/失败。
- 数据/UI/测试。
- 不做什么。
- 开放问题。

一个系统一页；不要写代码。

### 4. Tech Plan（技术方案）

复制 `references/tech-plan.md`，写：
- 要改/新增的文件。
- 场景/节点/信号/数据。
- tick/性能影响。
- 存档影响。
- 测试计划。
- 风险/回滚。

### 5. Task Breakdown（拆任务）

每个任务 0.5–2 小时，能独立验证。
复制 `references/task.md`。

任务顺序：
1. 数据/纯逻辑 + 单测。
2. 场景/组件。
3. 接 UI。
4. 接存档。
5. 视觉/手感。
6. 文档。

### 6. Implement（一次一个任务）

```
按 task.md 实现第 1 个任务。
只改列出的文件。
每完成一个文件跑 python tools/godot.py check。
失败先贴错误，不要继续加功能。
```

### 7. Verify（对照验收）

- 每条验收标准逐条确认。
- 贴命令输出/截图/日志。
- 没验证的明确说“未验证”。
- 发现偏差：先改设计/验收，再改代码，不要偷偷放宽。

### 8. Document（收尾）

- 更新 `design/systems/<name>.md`。
- 更新 `docs/DECISIONS.md`（如果有决策）。
- 更新 `docs/ROADMAP.md`（完成/顺延）。
- 写 3 行变更总结。

## 设计笔记的“好”标准

- 一个新人能照着实现 80%。
- 有玩家决策，不只是系统描述。
- 有优先级/边界/失败。
- 数值有单位/范围/默认值。
- 有 Given/When/Then 验收。
- 有“不做什么”。

---

## 验收标准怎么写

### 坏
- “工作系统能工作。”
- “UI 好看。”
- “性能优化。”

### 好
- “饥饿值从 100 以 4/游戏小时 衰减；到 20 时 Pawn 优先寻找食物；没有食物时到 0 开始掉血，每秒 1 点。”
- “1280×720 下，HUD 的时间/资源/选中面板不重叠；选中单位时需求条每 0.2s 更新。”
- “12 Pawn + 100 建筑 + 夜间，平均 FPS ≥ 60，1% low ≥ 45。”

### Given/When/Then

```
Given 一个饥饿值 10 的 Pawn 和 3 个食物
When  推进 1 个游戏小时
Then  Pawn 认领“吃”工作，移动到最近食物，饥饿值恢复到 80+
```

---

## 任务拆分示例：加“饥饿”

| # | 任务 | 验收 |
|---|---|---|
| 1 | `NeedDef` + `NeedsComponent` + 单测 | 衰减/阈值正确 |
| 2 | Pawn 场景挂 `NeedsComponent` | 运行 10s，值下降 |
| 3 | `JobBoard` + “eat” Job | Pawn 能认领/完成 |
| 4 | 食物实体 + 储物区 | 吃完数量减 1 |
| 5 | HUD 需求条 | 选中时显示/更新 |
| 6 | 存档/读档 | 饥饿值 roundtrip |
| 7 | 边界：没食物/食物被拿走 | 不卡死，给出提示 |

每个任务都能独立跑 `check`。

---

## 处理不确定性：Spike

如果某个方案不确定（API/性能/手感）：

1. 在 `prototypes/` 建一个**一次性**最小场景。
2. 时间盒 1–2 小时。
3. 只回答一个问题（“A* 1000 格要多久？”“TileMapLayer 能承载 512×512 吗？”）。
4. 记录结论到 tech plan/ADR。
5. **不要把 prototype 代码直接搬进正式代码**；重写干净版本。

---

## 范围守卫

出现以下信号，停下来：

- 任务超过 2 天还没可运行结果。
- 改了 10+ 文件还没验证。
- 开始做“以后可能用得上”的抽象。
- 开始加第 3 个新系统，而第 1 个还没玩。
- 设计文档越写越长，但没有可玩构建。

对策：砍到最小可玩，先验证核心乐趣。

## 和 AI 的对话模板

### 开始
```
读 AGENTS.md、docs/GAME-BRIEF.md、design/systems/<name>.md。
目标：<一句话>
约束：<不能改什么>
验收：<3 条>
先给设计笔记/技术方案/任务拆分，不要写代码。
```

### 实现
```
按 task 1 实现。只改 tech plan 列出的文件。
每步跑 check；失败贴完整错误。
```

### 验收
```
对照验收标准逐条确认，贴输出/截图。
未验证的明确说未验证。
更新 design/docs。
```

---

## 反模式

- ❌ 一句话需求直接生成 2000 行。
- ❌ 先写 UI，再想数据。
- ❌ 验收标准是“能跑”。
- ❌ 测试只覆盖 happy path。
- ❌ 设计文档和代码不一致，且不更新。
- ❌ 任务太大，三天看不到可玩结果。
- ❌ 用 prototype 代码直接上线。
- ❌ 决策只在聊天里，不写 ADR。
