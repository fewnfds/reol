# 规格驱动的游戏开发

当需求、状态所有权、风险或验收尚不清楚时，先把目标与最小可验证范围写清；明确的小修复可直接实施。用户已确定的方向不重问，常规技术选择按项目上下文处理；只有真正阻塞的问题才需要澄清。

## 工作方式

1. 结合 `docs/status/features.md`、`docs/engineering/architecture.md` 和相关设计，区分玩家意图、已实现功能与未来方案。写明目标、限制、边界和可观察验收。
2. 按需要记录方案、所有者、共同时间/取消、资源、存档迁移、依赖及风险；把工作拆成可验证的小包。不要先假设要新建完整系统或重做旧功能。
3. 完成已授权实现，先跑受影响的定向验证，再在合适的验收点按 `godot-verify` 和 `AGENTS.md` 执行必要完整检查；不要每改一个文件就重复全套。
4. 对照验收检查行为、失败与证据，设计变化更新领域候选，进度只更新status、详细结果放QA；清楚区分已验证和未完成，不为了通过测试放宽原合同。

需要文档时按任务选用模板：[设计笔记](references/design-note.md)、[技术方案](references/tech-plan.md)、[任务](references/task.md)、[ADR](references/adr.md)。模板不是强制流程；简单、可逆的工作不必创建整套文档。
