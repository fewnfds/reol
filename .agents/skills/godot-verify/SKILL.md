# Reol 验证

结论必须有对应命令输出、日志或实际画面；清楚说明覆盖范围、失败和未验证项。先查看 `docs/BASELINE.md` 的当前版本及既有证据；引擎目标跟最新稳定版，但不要把其他版本的结果当作当前验证。

## 按变更选择验证

- 文档、技能或配置文案：检查结构、链接与差异；没有游戏行为变化时不必运行游戏或完整游戏回归。
- 游戏逻辑/数据：优先定向测试真实行为和相关边界；新资源或全新检出先导入。按 `AGENTS.md` 的游戏行为完成要求，在合适的最终验收点运行一次 `python tools/godot.py check` 或由项目已有 CI 完成并核对结果；不要逐文件反复跑完整套件。
- 存档/跨时间状态：验证 roundtrip、相关历史档迁移、进行中恢复及关键失败边界，不覆盖旧 fixture。
- 画面或交互：实际启动并观察相关流程、窗口尺寸、截图和游戏/编辑器日志；headless 运行不证明视觉正确。性能问题先量测目标场景。

## 运行器与错误

`python tools/godot.py test` 启动 `tests/run_tests.gd`；`check` 还做结构检查和导入。包装器记录 stdout/stderr、非零退出、超时及 `SCRIPT ERROR:`/`ERROR:` 行；不要只看断言汇总。必要时以正整数 `--test-timeout` 给长回归指定上限。

现有 runner 同步调用 `test_*`，不自动等待测试返回的协程。需要帧或信号的异步测试时，先设计并验证真正会等待、能超时且失败会传到退出码的执行路径；不能仅往现有同步用例里加 `await` 就声称覆盖。裸 `assert()` 或 `push_error()` 也不能单独保证进程非零退出。

排错先读首个解析/运行错误及其位置，修复后重跑受影响的验证；出现新改动或失败才扩大/重复检查。MCP 的成功响应、状态或截图各自有范围，不能互相替代；如果测试无法执行，说明原因和剩余风险。

遇到导入、缓存、场景或测试失败时，按需读[排错要点](references/troubleshooting.md)。
