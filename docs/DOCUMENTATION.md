# 文档分类与维护合同

文档按问题分类，不按聊天或开发日期堆积。入口是 [README](README.md)；本页只规定放置位置、权威边界和维护方式。

## 唯一职责

| 类别 | 位置 | 应写什么 | 不应写什么 |
|---|---|---|---|
| 游戏愿景 | [design/vision](../design/vision.md) | 游戏体验、范围和长期方向 | 当前版本、测试数、工作进度 |
| 已确认世界规则 | [design/rules](../design/rules/README.md) | 用户确定的世界法则、明确未决项 | 开发候选公式、实现状态 |
| 详细设计与候选 | [design](../design/README.md) 的 systems、proposals | 机制、条件、失败后果、备选结构 | 把提案写成已确认概念或已完成代码 |
| 研究 | design/research | 来源、可借鉴机制、限制、许可候选 | 把竞品做法当项目承诺 |
| 工程约束与实际结构 | [engineering](engineering/README.md) | 状态所有者、依赖、兼容、工具及工作流 | 目标模块冒充已有系统、历史任务流水 |
| 未来依赖与工作包 | [plans](plans/README.md) | 建议顺序、范围、停止扩展点、验收出口 | 自动执行授权、实际完成宣告 |
| 详细工程规格 | [specs](specs/README.md) | 接口与迁入候选、长期技术合同 | 第二套当前任务队列 |
| 当前状态 | [status](status/README.md) | 当前任务、真实功能边界、版本证据、分支快照 | 长期设计全文、已结束包的流水账 |
| 验证证据 | [qa](qa/README.md) | 受检 SHA/负载/结果/限制，指向原日志 | 以后版本自动继承通过结论 |
| 决策来源 | [decisions](decisions/README.md) | 取舍的来源、当时理由 | 旧 ADR 自动覆盖用户较新决定 |
| 历史 | [archive](archive/README.md) | 原规格、旧顺序和接续、原报告 | 当前 active、下一包或永久兼容要求 |

当前任务只有 [handoff](status/handoff.md) 一处；基础工作依赖只有 [foundation-priorities](plans/foundation-priorities.md) 一处。长期产品目标不构成另一条执行队列。

## 状态与冲突

- **已确认概念**不表示已实现；**候选设计**不表示用户拍板。
- **现有范围可用**必须写清实际路径；**专用样本**不表示通用接口完成。
- **隔离候选**有代码但未接普通世界；**待验**缺对应版本所需证据。
- **历史记录**中的 active、下一步、版本和数字只描述当时。

冲突先区分概念、候选、代码和证据。概念遵循用户较新明确指令；行为由实际代码与运行决定；通过结论由具体版本和验证范围决定。代码偏离概念应登记缺口，不能靠改写概念消除。只有改变概念且无法由上下文判断时才向用户提问。

普通世界、隔离候选和通用接口的当前接入程度只查 [FEATURES](status/features.md) 与 [BASELINE](status/baseline.md)，不在本治理页保存实现快照。已确认环境规则在 rules，具体曲线和参数在候选设计。旧 W/F/A 编号只保留追溯意义，不继续决定实施顺序。

## 文件大小与修改

1. 每次只读任务所需入口和领域页，不把整个目录加载成提示词。
2. 活跃文档以 4–12 KiB 为宜，超过 16 KiB 按独立主题拆分；原路径成为短索引，子页按主题命名。历史原文、证据与来源技能参考可保留原长度。
3. 新状态只更新对应 status 页；包完成后详细结果放 QA，handoff 只留继续工作所需信息。不要在设计或每份计划末尾追加进度。
4. 重要重写保留 Git 来源或历史副本。迁移同步修改链接、技能入口、工程检查和目录；历史 fixture、日志、截图不因新结论被重写。
5. 链接使用相对路径；跨文件引用优先链接主题页，避免依赖易变的长标题锚点。
6. 结构/链接/大小检查只证明文档组织，不证明游戏行为。文档整理不启动 Godot；必要 Python 检查按修改范围验证。
7. 优先更新已有主题页；新增文件须有独立职责。小包不机械创建整套计划/规格/进度/报告，ADR只记录实际新决策。基线不复制QA流水，handoff只存当前停点；详细历史留原证据和Git。
