# 提交、Codex审查与CI

更新：2026-11-04。依据当日实际读取的[桌面审查](https://developers.openai.com/codex/app/review)、[GitHub集成](https://developers.openai.com/codex/integrations/github)、[官方Action](https://developers.openai.com/codex/github-action)及[计费说明](https://developers.openai.com/codex/pricing)。本机CLI为`0.166.0-alpha.6`，`codex review --help`已核对；未升级客户端或改变模型。

## 采用的流程

每个可解释的工作包：开发与定向验证 → Git提交 → 一次原生Codex审查 → 修复有效问题 → 推送与一次对应版本CI → 记录结果。以具体提交及代码差异为审查对象，不以聊天历史为唯一依据。文档小改仅检查结构、链接及差异，不启动模型审查或完整Godot回归。

- 开发期间仍使用任务说明、AGENTS和按需技能。子代理用于可并行实现或明确专项调查，这也是Codex支持的工作方式。
- 普通代码包默认用原生审查作为主要审查。需要独立的存档、时间、空间或性能审计时，才派一个有明确范围的专项代理；不让多个审查者重复读同一整包，不每次小修改重跑整轮审查。
- 审查发现先核实触发条件、代码路径和影响，再决定修复；无实质发现即可结束。审查无发现不代表测试通过，CI成功也不代表世界规则或画面正确。
- 默认只报告能说明实际后果的问题，机械检查交给现有工具。代码审查规则见根目录[AGENTS.md](../AGENTS.md)的`Code Review Rules`，不另造第二套长期提示词。
- 修复会生成新SHA。保留旧审查记录，只补查改动及受影响路径；CI证据必须对应最终提交，不能沿用修复前的绿色结果。

## 现成的审查入口

| 入口 | 使用方式 | 适用场景 |
|---|---|---|
| 桌面原生审查 | 在Codex输入框输入`/review`，选择未提交改动或基准分支；结果可在差异面板查看 | 本地工作包，已有Git仓库即可 |
| CLI原生审查 | 以下`codex review`命令，输出有优先级的问题，不主动修改工作区 | 精确到一次提交，适合当前分支历史较长的情况 |
| GitHub原生PR审查 | 将仓库连接到Codex，在Codex设置中启用仓库审查；PR评论`@codex review`，或按所选事件自动触发 | 云端PR审查和留存反馈；当前官方说明默认聚焦P0/P1 |
| 桌面Code Review插件 | 连接源码账户，打开PR链接，查看描述、差异、评论和checks，选择`Review with Codex` | 在应用里查看PR及CI、调查失败；聊天审查不自动发布或合并 |
| 官方`openai/codex-action` | GitHub Actions中调用Codex，使用API密钥和受限权限 | 将模型任务纳入可重复CI；本项目暂不采用 |

已核实的CLI命令（在项目目录执行，选择一种）：

```powershell
codex review --uncommitted
codex review --commit <完整提交SHA>
codex review --base <明确基准分支>
```

`--uncommitted`包含已暂存、未暂存和未跟踪文件。工作区混有半成品时，优先审查已隔离提交，避免把全部草稿带入。`--base`审查分支自共同祖先起的差异，不是只看最后一包。审查期间停止修改其目标；修复另开步骤。

桌面`/review`与PR插件是两个入口；侧栏安装插件不等于已启用GitHub云端自动审查，`gh`登录也不能证明Codex仓库连接已经完成。本轮未核实账号侧连接，未启用自动审查、发布机器人评论或新增付费Action。

## GitHub与CI怎样配合

CI负责执行确定性的检查和测试；Codex负责理解差异、找行为与架构问题。两者结果都可在PR上查看，审查不替代CI或分支保护。当前仓库只有CI，没有自动发布、导出发行包或部署的CD。

本轮审计时仓库没有打开的PR，最近CI由分支推送触发。现行[workflow](../.github/workflows/ci.yml)同时监听`push`和`pull_request`：同仓库分支建立PR后，再推送可能触发两次完整回归。两个run可能分别测试分支提交和PR合并结果；现有按`github.ref`分组的并发设置不能可靠去重，也不能把两种SHA混作同一证据。

因此采用分阶段切换，**本轮不改变触发器**：

1. 当前仍按工作包提交、精确提交原生审查、分支推送CI，维持现有覆盖。
2. 整理历史集成基线，再采用小PR。审计时`codex/world-engine`相对`main`已有14个提交、230个变更文件；不能把这段历史伪装成一个很小的新功能PR，也不自动合并或改写历史。
3. 正式采用PR流程时，将重型CI改为PR更新、默认分支推送及手动触发；未建PR的中间提交只跑定向检查，需要完整证据时手动触发一次。改触发器与建立PR流程同包交付，避免分支失去验证。
4. 若后来要求PR必需检查，先处理纯文档PR：现在`paths-ignore`会使整个workflow不运行。应始终给出轻量检查状态，再按改动选择重型Godot工作；不能直接把会跳过的检查设成必需项。

GitHub审查设置建议先用**手动每包一次**，避免每次推送都消耗模型。需要自动审查时再选择合适的`Review trigger`。云端PR审查和本地审查选一个作为该包主要审查入口；专项复核要有具体理由。原生GitHub集成走账户可用额度；Action要求单独的API密钥，API计费与订阅使用分开，不能当作免费CI测试。

用户需要操作的账号步骤只有：在Codex设置连接`fewnfds/reol`并开启该仓库的Code Review；自动审查另在仓库/个人偏好中配置。是否可用、额度和开关以实际账号界面为准。本项目已有`gh`和CI，不为查看同一仓库再安装一套GitHub MCP。

## 等待和验收

保留`tools/ci.py`的共享锁、缓存及同run至少300秒间隔。只由主代理登记目标run和完整SHA，必要时一个后台等待器处理；不派等待代理，不重复远程查询。

PR流程启用后需记录head SHA、实际受检的合并SHA及审查版本。CI结束后读取一次真实失败或成功证据；队列中、旧版本成功、机器人点赞都不是当前代码通过。涉及画面、音效、手感和声明规模的性能仍需要本机实际观察/测量。

这套流程不需要常驻的第二个Codex进程、自动修复循环或新增依赖。以后如果人工触发审查成为稳定瓶颈，再评估官方Action；届时固定Action/CLI版本，限制触发者和权限，审查输出与自动写回分开，不让公共PR内容取得密钥。
