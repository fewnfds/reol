> 新决策追加到文件顶部或底部，保持编号递增。

## ADR-0001 — 引擎、版本与语言

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：项目是 Godot 4.7.2 初始工程；开发者有 Unity 基础，无 Godot 经验；目标 2D 俯视开放世界/殖民 sim/RPG。
- **决策**：Godot **4.7.2** 标准版 + **GDScript**；不使用 C#/.NET；目标平台先 Windows。
- **后果**：
  - 可以使用 Godot 4.7 新特性（TileMapLayer、typed arrays 等）。
  - 不能直接复用 C# 生态/Unity 代码。
  - 升级引擎要跑全量测试和截图对比。
- **替代方案**：
  - Godot 4.7 .NET + C#：生态更强，但本项目不需要，且 Godot AI 对 C# 仅文本支持。
  - Unity：已有经验，但用户明确选择 Godot。

## ADR-0002 — 先做垂直切片，不做“大而全”

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：目标包含开放世界、建造、殖民模拟、RPG、战斗；一次性做完不现实。
- **决策**：v0.1 只做 **“One Camp”**：128×128 地图、1 玩家 + 3 殖民者、采集/建造/吃饭/睡觉/一次袭击/存档。
- **后果**：
  - 大量想法进入 backlog，不进入首个版本。
  - 每个系统必须服务于 30 分钟可玩循环。
- **替代方案**：先做纯 RPG / 纯殖民 sim / 纯建造；都会失去“组合”的验证。

## ADR-0003 — 视角与美术方向

- **日期**：2026-11-01
- **状态**：提议（待用户确认）
- **背景**：参考 Warcraft 的俯视角；开发者无美术团队；需要快速占位。
- **决策（建议默认）**：**2D 俯视 + 32×32 像素风**；先用 Kenney/LimeZu 占位；M4 再统一风格。
- **后果**：
  - 纹理 Filter 用 Nearest；相机/UI 按像素风调。
  - 不做 2.5D 高度层；遮挡用 Y-sort + 简单层级。
  - 后续转 HD/2.5D 成本较高。
- **替代方案**：16×16（更复古，细节少）、手绘 HD（成本高）、2.5D（复杂度高）。

## ADR-0004 — 架构：节点组合 + 数据驱动 + 固定 tick

- **日期**：2026-11-01
- **状态**：提议
- **背景**：殖民 sim 需要可预测的模拟；Godot 节点树适合组合，但 `_process` 不适合做模拟。
- **决策**：
  - 实体用 **Node 场景 + 组件子节点**，不做完整 ECS。
  - 定义/数值用 **Resource + JSON**，不硬编码。
  - 模拟用 **GameClock 固定 10 tick/s**；渲染/物理分开。
  - 系统间用 signal/EventBus 解耦。
- **后果**：
  - 需要自律：不在 `_process` 写模拟。
  - 实体数量上限比纯 ECS 低，但对 12–50 Pawn 足够。
  - 测试可以手动推进 tick，不依赖真实时间。
- **替代方案**：完整 ECS（过度）、纯节点每帧（不可测）、Unity DOTS（换引擎）。

## ADR-0005 — 世界模型：手工骨架 + 程序填充

- **日期**：2026-11-01
- **状态**：提议
- **背景**：全程序生成难做出“有意义的地标”；全手工地图内容量有限。
- **决策**：
  - v0.1：单张 **128×128** 手工/半程序地图。
  - v1+：**64×64 区块**，seed + 规则生成地形，POI 数据表放置，只存 deltas。
- **后果**：
  - 需要设计地图数据格式（JSON/ASCII）。
  - 需要区块加载/卸载/持久化。
  - 不能承诺“无限世界”。
- **替代方案**：全手工（内容少）、全程序（地标弱）、无限 chunk（性能/存档复杂）。

## ADR-0006 — NPC AI：Utility 优先，行为树为辅

- **日期**：2026-11-01
- **状态**：提议
- **背景**：殖民 sim 的日常决策（吃饭/睡觉/搬运/建造）适合效用评分；复杂战斗/逃跑适合行为树。
- **决策**：
  - 日常需求/工作：**Utility AI + JobBoard**。
  - 复杂战斗/逃跑/巡逻：可选 **LimboAI/Beehave** 行为树。
  - 不接 LLM 做核心决策。
- **后果**：
  - 需要可视化调试（为什么选这个工作）。
  - 行为树插件是可选依赖，不是核心。
- **替代方案**：纯 FSM（简单但难扩展）、纯 BT（日常决策笨重）、GOAP（过度）。

## ADR-0007 — 存档：版本化 JSON + deltas

- **日期**：2026-11-01
- **状态**：提议
- **背景**：殖民 sim 状态复杂；改字段频繁；需要可读/可迁移。
- **决策**：
  - `user://saves/*.json`，带 `version`。
  - 地形只存 deltas；实体存 ID/定义 ID/状态，不存节点路径。
  - 原子写：`.tmp` → flush → rename；保留 `.bak`。
  - 每次存档结构变更加迁移函数 + roundtrip 测试。
- **后果**：
  - JSON 体积较大；后期可压缩/分片。
  - 需要严格的序列化约定。
- **替代方案**：二进制（快但难调试）、Godot Resource（版本迁移麻烦）、SQLite（过度）。

## ADR-0008 — AI 开发工具链

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：需要让 AI 能读文档、看编辑器、跑项目、读日志、验证改动。
- **决策**：
  - 主 IDE：**OpenCode**（本项目）。
  - 技能：`.opencode/skills/`，按需加载。
  - 实时编辑器 MCP：**Godot AI**（v4.3.1，MIT）。
  - 无头/启动 MCP：**Coding-Solo godot-mcp**（0.1.1，MIT），通过 `tools/mcp/godot_mcp.py` 包装。
  - 文档：**context7**。
  - 验证：`tools/godot.py` + `tests/run_tests.gd`。
- **后果**：
  - 需要 Godot 4.7+ 和 Node 18+。
  - 两个 MCP 有重叠；约定日常用 Godot AI，CI/无头用 Coding-Solo/CLI。
  - 第三方插件有编辑器权限，需 pin 版本/审查。
- **替代方案**：只用一个 MCP（功能不全）、不用 MCP（AI 盲写）、Claude Code + Claude-Code-Game-Studios（流程重，非 OpenCode）。

## ADR-0009 — 技能库来源与固定版本

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：需要一套高质量、Godot 4.7 对齐的技能，而不是自己从零写。
- **决策**：
  - 从 **awesome-gamedev-agent-skills**（Apache-2.0）选取 Godot/通用/类型技能，vendor 到 `.opencode/skills/`。
  - 固定 upstream commit `19d93f97c9c1ea0f8b306e77aa81e0d3e352d3e9`。
  - 项目专属技能（架构/殖民/世界/验证/流程）自己写。
  - 保留 LICENSE/NOTICE。
- **后果**：
  - 升级需要手动 diff/重拷。
  - 技能是英文，项目文档是中文；AI 可以混用。
- **替代方案**：`npx skills add` 全量安装（含 Unity/Unreal 噪声）、只用 Claude-Code-Game-Studios（流程重）。

## ADR-0010 — 单人优先，不做联机/C#

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：联机/账号/服务器会显著增加复杂度；本项目核心是模拟与沙盒。
- **决策**：v0.1–v1 只做单人；不引入 C#；不做服务器权威/回滚网络。
- **后果**：
  - 可以使用简单的全局状态/暂停。
  - 后期联机需要重构，但那时玩法已验证。
- **替代方案**：一开始做联机（高风险）、C#（团队更熟但生态不需要）。

## ADR-0011 — 第三方依赖策略

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：Godot 生态插件多，容易堆叠失控。
- **决策**：
  - 优先内置能力。
  - 新依赖必须：支持 4.7、MIT/Apache/商业友好、近 6 个月维护、可干净移除。
  - 每个依赖记录版本/许可证/来源到 `THIRD_PARTY_NOTICES.md`。
  - 不装“可能以后用得上”的插件。
- **后果**：
  - 可能需要自己写 100–300 行，但可控。
- **替代方案**：自由装插件（快但风险高）。

## ADR-0012 — LLM 不进核心模拟

- **日期**：2026-11-01
- **状态**：已接受
- **背景**：Microverse 证明了 LLM NPC 的趣味，但 API 成本/延迟/不确定性不适合做核心需求/工作/经济。
- **决策**：
  - 核心模拟（需求/工作/战斗/经济）用确定性规则。
  - LLM 只用于可选对话/风味/文本生成，后期再做。
  - 不把 API key 写进仓库；不做离线依赖。
- **后果**：
  - NPC 对话初期是模板/分支，不是自由生成。
  - 游戏可离线运行。
- **替代方案**：LLM 驱动 NPC（成本/稳定性风险）、本地小模型（性能/质量风险）。
