## 1. 三层交付及推进方式

在Godot之上建立Reol专用的世界模拟层与创作工具。Godot继续负责窗口、输入、渲染、音频和基础编辑；原纯GDScript规则、共同时间和存档继续作为起点。

```text
内容创作：材质/物种/物品定义 + 地理/地图/建筑模板 + 开局/组织/工作装配
                              ↓ 校验、生成独立候选
世界运行：身份/位置/容器 → 空间/导航 → 环境 → 动作/交互/生活
                              ↓ 有限认知查询
游戏呈现：人物/瓦片/八向外观、界面、特效、声音

开发工具：编辑定义与布局 → 隔离预览/暂停/快进 → 热图/原因/错误 → 保存内容
玩家改造：感知/能力/权限 → 实际行动/成本/耗时 → 修改同一世界
```

每项基础先有可运行规则，随后配最小编辑与观察工具，再用其创造内容；不用等完整引擎结束才验证，也不先写一套庞大编辑器。首轮让创作者能修改地图、单位和灵物后得到可解释结果；海量装备、种族、剧情和房型在公共能力稳定后再补。

## 2. 优先完善的八项基础

|---|---|---|---|

| 8 持续性、可解释性与规模 | 共同边界、远区批算、稀疏状态回收、原子恢复、预算与性能报告 | 隔离预览、固定seed、对照运行、原因查询、压力报告 | 每项都要测存读/性能；最终再做联合规模验收，不能拖到末尾补连续性 |

### 实体与属性的实际含义

共同入口回答“这是谁、属于哪类、在哪里、占多少空间、能做/接受什么作用、由谁保存状态”。地块采用空间键批量保存，不为每格生成节点或人物式实体。植物、活物、物品和结构都能被引用/观察，但更新精度和拥有的能力可以不同。

定义保存材质、身体形态、体型、可用感知/移动/交互能力与默认响应；实例保存实际位置、数量、温度/储能、伤势、经历与个人知识。属性分为原始事实、动态状态、派生能力、观察者所知四层；没有某种能力不等于有一条零值属性。树、麻雀、魂与巨兽不强塞同样的饥饿/装备/灵气字段。

受控生成读取定义与开局，验证地形/净空/承载，再由原领域分配实例、登记引用和建立视图；失败不留半个单位。移除须结清引用、预约、物资、环境来源和原有后果，不把销毁画面节点当作死亡。自然出生、成长、繁殖和有限转生仍是后续具体规则，不由生成按钮冒充实现。

### 物品、归属与状态

位置/保管与法律或社会归属分开：偷来的东西能在行囊里，委托搬运不自动成为可花的私人财产。嵌套容器不得成环；容量、承载和不同场透过率由定义决定，物品发光/冷热/灵机沿原位置链解析。

同质物资按批次数量；个别具有独立储能、损伤、铭记或产权差异时按明确规则拆批或成为独特实例。合并须保数量、状态和归属，不能把一枚独特法器既记在数量账又复制为独物。首版完整支持已有物资/法器/衣物接缝，再逐步开放容量、负重、任意地面放置等；不同时泛化全部物品种类。

### 导航与动作的实际含义

连续位置用于实时移动和战斗，格子/区域用于空间、寻路与建造。导航读真实地形、门、结构和身体净空，按步行/飞行/体型分查询；局部路径与跨区域路线分层，重规划有预算，不因不可达穿墙或瞬移。先比较现有局部搜索与所需范围，再据测量决定A*、分区路径或其他内置方案，不能先承诺一种算法包办全部。

命令/动作数据包含发起者、动词、对象、条件、规则版本与结果引用；输入、NPC和未来AI都通过已支持的入口，不能直接改真值。请求受理、对方理解/愿意与真实执行分别记录。原行为逐个接共用生命周期，不强迫每种动作使用相同阶段或复制旧过程。

战斗、法器使用和修炼将复用目标/感知、连续空间、成本、过程与效果接口；具体招式、伤势、境界仍另行实现，不把环境改造同时扩成完整战斗项目。任务与社会记录通过真实执行结果形成，不由编辑器直接发“玩家已完成”的奖励。

## 3. 实施依赖与阶段出口

| 阶段 | 先完成 | 紧接的工具与验收出口 |
|---|---|---|
| A 状态合同与内容入口 | 第1项，及第2/3项必需的ID、位置/保管和生成；保留可验基础、隔离争环半成品 | 定义验证器、只读对象/来源检查、最小放置入口；生成/转移/失败与存读可重复 |
| B 可改造空间 | 第4项，完善第2/3项空间需求，接现有门墙顶和真实物品 | 地形笔刷、物品/单位摆放、拖线/框墙、自动连接；改造同时影响显示、路径与围合 |
| C 地理与多场运行 | 第5项，沿环境W1、W2a冷热、W2b照度、W2c灵机分段接入 | 气候与来源编辑、热图/原因检查；任意布局多源叠加、移动、遮挡、拆墙、离场和存读 |
| D 共同过程与世界响应 | 第6/7项最小可复用范围，补导航/动作的动态重规划与预约 | 工作台/设施/区域组合及NPC有限安排；同一能力被玩家、NPC和不同内容复用 |
| E 用工具构世界 | 各阶段接口稳定后补可复用模板与校验，不等所有NPC智能做完 | 用编辑工具装配山地、灵地、住处/值事房/工坊及不同生物/灵物；普通新局可进入 |
| F 联合稳定性 | 汇总第8项；每阶段原已持续检查的迁移、近远区与性能 | 从创作到新局到玩家改造，再离场/返回/保存重启的完整出口，记录真实规模和边界 |

每阶段只迁移实际需要的接缝。不能因为名字叫“引擎”就停做可运行的游戏，也不能靠完成一面板宣布规则已完成。环境W0/W3等子项穿插A/B/C，W4/W5穿插D/F；八项是职责，不是八套新autoload。

A/B是阶段汇总，拆成独立工作包：A0先做版本化内容/开局与独立候选装配、旧档兼容；A1接至少一种已有生命和一种已有物品的生成/位置/一次转移；B0接一种持久地形改造及显示/阻挡查询失效；B1接墙门/围合与最小画笔。各包分别验存读和可观察结果，批量蓝图、更多身体/容器和跨区导航随后扩展，不能把A/B整体塞进一次大改。

## 4. 创作工具：先提供哪些编辑能力

| 工具 | 能编辑或观察什么 | 第一版交付方式 |
|---|---|---|
| 定义编辑 | 地块/材质、物种身体、物品、来源/响应、可用动作的参数和引用 | 原JSON规范、校验与简易属性表；按需用Godot Inspector呈现 |
| 地图/空间编辑 | 地表/高度/材质、真实结构、门顶、放置点及区域 | 少量笔刷、拖线/矩形、吸取、预览与非法原因；复用Godot瓦片能力 |
| 对象装配 | 已支持单位/物品的模板、数量、初始状态、容器和关系 | 调色板+属性检查，保存场景装配数据，不另造模拟状态副本 |
| 环境编辑 | 地理范围、天气参数、灵物来源、材质导通/屏蔽与响应 | 曲线/参数表+可切覆盖图，能追到原来源、条件与实际消耗 |
| 模板/开局编辑 | 房屋、地点、家具、库存、人员/岗位、起始知识与有限工作安排 | 组合模板展开成真实实例并重映射内部ID；外部引用明确，不能复制独物历史 |
| 运行检查 | 开始/暂停/快进、过程/来源、物资/能量账、保存重启与性能 | 独立预览会话、最小调试面板及现有CLI测试；普通玩家界面仍受认知限制 |

优先Godot现有Inspector、TileMapLayer和少量项目自有面板；反复验证编辑负担后才增加EditorPlugin/InspectorPlugin。自有工具与第三方addons清楚分开，第三方源码不改。不先开发通用可视化脚本语言、完整节点图编辑器或新的通用引擎编辑器。

现有JSON定义/开局保持唯一可持久来源；若用Resource帮助Inspector编辑，作为明确适配视图，验证后写回同一份数据，不同时维护JSON与tres两份权威内容。不把运行伤势、余额、个人经历写回共享模板或TileSet。运行状态也不能直接指向会被编辑器修改的共享资源。

### 开发创作、预览与玩家操作

- 创作模式修改定义草稿或开局布局，提交前验证字段、引用、范围、承载和循环；可直接布置但不得破坏底层不变量，不伪造玩家劳动/付款历史。
- 预览模式从草稿创建独立候选，确定seed和规则版本后运行；默认停止时丢弃预览的运行变化，可单独保存开发快照。首版不把已经模拟过的伤势、消费与历史自动烘焙成新的开局。
- 玩家模式在实际世界中通过本人感知/能力、社会权限、材料、耗时和中断改变世界。开发工具看到全量真值不意味着玩家获知它。
- 撤销/重做只作用于编辑草稿。预览已推进时间后，用独立快照重置到基准，不能只撤掉墙却假装热扩散、NPC行动和物资消费也已倒流。
- 编辑模板不会自动更改已存在的实例或存档历史。定义ID、规则版本和开局/生成版本有清楚兼容策略；新能力从明确边界启用，旧档经原候选流程迁移，不重写历史fixtures。

### A0必须先解除的两处现有耦合

当前人身体力恢复在`village_simulation.gd`中仍按`definition_id`读取当前`_content`的上限，恢复也基于当前内容校验；直接改同ID的JSON可能改变已有实例行为或令旧档失效。因此首版会话绑定不可变内容包，保存实际依赖的数据定义快照、开局基线与版本/摘要；预览或新世界选新版，原会话继续原包。规则代码版本另行兼容/迁移，不假装有数据快照就能运行任意历史代码。无版本旧档只按已知历史基线迁移，不能用今天的定义猜过去。

当前`WorldSessionSnapshot.stage`虽不先改活世界，但仍借当前adapter的区域、人员、地点和opening_config建候选，并限制home/river与centers。它是原双聚落恢复接缝，**尚非任意创作世界工厂**。A0需让候选根据自己的版本化内容/开局/地图基线构造和联合校验，活场景只在接受后绑定；新工厂逐步接回原正常读档，保留双地旧档迁移。

A0验收包含：相同定义ID修改容量/材质前后的两个内容包，旧实例和旧档保持原行为，新世界使用新版；两份不同布局/人员的候选互不依赖，分别启动及来回存读，失败不更改活世界。相关现状依据见[人物运行代码](../../scripts/sim/village_simulation.gd)、[联合候选](../../scripts/runtime/world_session_snapshot.gd)。

## 5. 内容如何建立在架构之上

以“寒光石”和山中小院为创作例子，不为它们编剧情：

1. 从已有物品模板创建新定义，选择已支持的吸热源和微光能力，填写容量、功率、消耗及材质；此时不新增专门的寒光石脚本。
2. 在空间工具中修改地表，画墙门与屋顶，摆放真实石头、火源、柜子和不同生物；保存为地点模板或开局。
3. 隔离预览观察冷热、照度、灵机及受体行为，检查来源与总账；搬石入柜、开门、拆墙并比较结果。
4. 校验后作为内容进入普通新局。玩家按正常规则改造，NPC使用同一空间与环境；离开返回和重启后保持实际结果。

同类地块、物品、建筑布局和已有能力组合应主要改数据；全新身体结构、传播规律、动作语义或生命过程需补运行代码、校验和测试，之后才进入编辑器。编辑器不会凭文字生成未知规则。正式美术继续后置，代码示意图保持可读。

## 6. 文件职责与验收

沿用现有目录：`scripts/sim/`保存规则/权威状态，`runtime/`连接输入和视图，`persistence/`处理文件与迁移，`data/definitions/`保存定义，`data/scenarios/`保存开局/装配，`tools/`保存离线校验/开发工具。若需要Godot插件入口，按官方布局放独立的项目自有插件，纯规则不移进插件。当前只写计划，不提前创建空目录。

每个运行模块和对应小工具一起验：定义→校验→放入候选→运行→实际改造→离场→存读→恢复。至少两种内容/布局复用同一机制，并覆盖非法引用、重叠/不可达、容器成环、重复提交、多源竞争、改结构、能力不适用及旧档迁移；不以单个精调事件证明通用性。

开发观测包括事实、来源、时间、费用与失败原因；覆盖图仅是可检查投影。热/灵机等存量对账，光照检查来源/遮挡，行为检查请求与结果是否分开。性能按活跃单元/对象/源/路径/结构变更逐级施压，记录帧时、模拟耗时、内存和存读；不预先保证任意地图规模。

完整回归沿现有CLI/CI，精确到相应提交；CI遵守五分钟节流、不派等待代理。纯文档本轮只查结构、链接和差异；既有半成品不提交进一个虚假的“引擎已完成”版本。

## 7. 近期实际出口
