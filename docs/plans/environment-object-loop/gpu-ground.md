# 下一小包候选：真实地面来源的 GPU 加速

本文记录本包实施规格，不承担当前状态和证据职责。用户随后已授权实施；完成范围与待验出口只看[接续](../../status/handoff.md)和[QA](../../qa/20261105_environment_ground_compute.md)。这一包完成后停止，是否进入下一包再讨论。

## 为什么排在这里

第二阶段 A2a 已能从真实地面实物和材料堆装配五行/冷热的**基础目标缓存**。在每格一个真实来源的 512×512、半径 16 负载下，CPU 选定全区域冷建累计约 19.26 秒（其中一个 16×16 窗口已预热）；1% 分散物件变化后的重建累计约 19.40 秒。计算分片执行，这不是单帧卡顿时间，也不代表普通游戏当前的帧率。

项目已有独立的 GPU 计算服务。在 512×512、半径 4/8 的**合成来源**负载中，其一次场计算端到端约 160 毫秒，但此结果不包含真实原物装配，与上面的真实原物 CPU 数字不是同组对照，不能直接相除或承诺提速倍数。来源：[真实缓存 QA](../../qa/20261105_environment_ground_cache.md)、[GPU 原型 QA](../../qa/20261105_field_compute_acceleration.md)。

本包只做一件事：**让同一份真实地面来源缓存可选地交给 GPU 计算，并用相同负载核对结果和端到端性能**。它是通用环境底座，不针对特定物品，不改变五行/冷热规则。

这是针对实测吞吐的性能前置，不是连续响应在逻辑上的硬依赖；本包不延伸为通用 GPU 框架。若真实负载没有收益，记录原因并保持 CPU 默认，结束本包后回到环境响应接合，不持续扩优化。

## 输入、输出和范围

```text
真实地面物品/材料堆
  → 已有来源投影（唯一原物、位置和数量）
  → 按区域请求基础目标块
  → CPU 或 GPU 使用同一份来源快照计算
  → 校验来源仍有效后发布完成块，供开发查询
```

数据仍由原世界拥有；GPU 只接收一次计算所需的只读副本，不拥有物品、场的历史、世界时钟或存档。五行和冷热取值、衰减、冷热抵消、同类堆只按一份强度计算，都沿用 A2a 的版本化规则。GPU 的整数结果与同规则 CPU 结果应完全一致。

本包开发接口支持明确选择 CPU/GPU，允许根据实测选择自动策略；不新增玩家设置，不切换普通 Main 旧冷热系统。无设备、任务过大、显卡报错或过期结果时，明确记录原因并回退到有预算的 CPU 路径，不把待计算当作零或已完成。

## 实现步骤

1. **整理真实缓存与计算服务的接缝。** 复用 `SimEnvironmentGroundCache` 和 `EnvironmentFieldComputeRuntime`，在运行层组织请求与回收；模拟规则不反向依赖渲染运行层。给真实缓存增加最小、受控的快照和发布校验接口，不暴露可绕过原物校验的通用写入口。已提交底层缓存已有导出/发布能力，先对 HEAD 核验，四份保护 WIP 不作为实现前提。
2. **装配并请求。** 来源投影完成、需要计算的块登记后，统一选定计算区域；小请求可以留在 CPU，大请求才考虑 GPU。拆清来源同步与目标重建的推进职责：一个请求只有一个计算后端驱动，不能让 ground advance 和计算服务重复重建同批块。每个时段的工作继续按预算推进，不能由于启用显卡而在主线程同步等待计算完成。
3. **防止旧结果混入。** 原物刚改变时，现有缓存先登记失效、之后才同步更新派生来源；因此仅核对底层场缓存的 revision 不够。快照和发布都核对原世界及缓存绑定身份、配置、来源变动代次、待同步队列和结果版本；变化、恢复或重新绑定后，旧计算只能丢弃，不得发布成当前结果。发布前在原 owner 线程复验，复验与发布之间不调用外部回调。物品合法变动不因缓存等待而失败。
4. **处理取消和退出。** 显卡线程只处理脱离原世界的快照；取消或换世界先令旧结果失效，再由拥有者继续回收线程。当前服务忙时 `close()` 会拒绝关闭，不能丢掉最后引用；需明确关闭中的状态和回收职责，避免主线程等 GPU 或释放仍运行的线程。驱动异常的退出耗时须实测，不能承诺硬实时上限。
5. **同负载比较并决定策略。** 先以 CPU 为正确性参照，再分别测试强制 GPU、CPU 和自动选择。只在实际测到端到端收益且主线程成本可接受时推荐自动 GPU；较小范围或持续过期任务可回退 CPU。不要预设合成数据上的阈值适合所有真实场景。

CPU/GPU 不应各自生成两套不同的来源规则。首次快照打包、块发布、内存分配和线程回收并非都受当前 `advance` 工作计数约束，必须计入测量；如同步步骤造成明显尖峰，应在本包内处理或明示没有达到目标，不能只报告 GPU 核函数耗时。

静态准入核对：512²、每格最多一个来源、半径 16 的主要输入数组约 12 MiB；单行估算为 `512×31×31=492032`，在当前快照与设备工作守卫内。此结论只证明代码允许尝试，不证明实际成功或性能；更大地图、多源同格或特殊半径需拆任务或明确回退，不扩充本包规模承诺。

## 功能验收

| 测试 | 预期结果 |
|---|---|
| 多种真实实物和材料、不同半径、冷热及五行 | 小图逐格逐通道 GPU 与 CPU 完全一致，实际使用到硬件 GPU；无设备回退不能算 GPU 测试通过 |
| 同类一堆 1/10000 份、最后一份移走、强源离开 | 强度、弱源接替和失效结果与 CPU 一致，不按数量放大 |
| GPU 运算时移动、拆合、移除或更换原世界 | 旧结果不能发布为当前值；受影响区保持待算，最终结果与新世界 CPU 对照一致 |
| 密集变化、重复请求、取消和关闭 | 不暴露半块或丢待算请求；线程有明确拥有者并被回收；不无限排队或一帧内全图重算 |
| 无渲染设备、超出设备约束、GPU 失败 | 有明确原因并可用 CPU 续算，不改世界事实；不能将 CPU 回退伪装成 GPU 加速 |
| 恢复与重绑 | 新世界不接收旧世界结果；缓存可由真实原物重建，不增加新存档事实 |

对于持续发生的来源变化，已有基础目标缓存允许合并待同步变更；这**不代表**未来实际温度可跳过中间历史。下一个连续响应包仍须在每个相关游戏时刻先结旧段、再接新段。

实施时由主代理先跑 doctor 和定向规则/真实 GPU 验证；整包一次原生只读审查，修复后以不含四份 WIP 的准确提交运行一次完整 check，或采用对应 SHA 的 CI 结果。GPU 验证必须实际使用设备，完整 headless 回归不能代替它。CI 仅在真实提交检查点查看，不等待或轮询。

## 性能测量和取舍

- 以[全项目性能基线](../../engineering/architecture.md#全项目性能基线)为准：PC、16 GB 整机、单张 RTX 3060 级显卡；约 10 GB 游戏进程占用是用户接受的量级，不是要求或模块上限。已有 GPU 工作缓冲和测试守卫是实现保护，不是整款游戏的内存预算；若成为瓶颈，结合实测和设备限制调整。
- 在同版本、同真实原物、同区域、同半径/变化序列下，至少比较 64²、128² 和 512²，覆盖半径 16、混合半径、局部读取及 1/16/64 件、1% 分散变动。512² 使用真实实物和材料堆，分开记录装配、首次场建立、一次变化到结果可读；小图全量对照，大图标明全量或抽样范围。
- 记录实际 CPU、显卡名称、内存和 Godot 版本；分别给出从请求到可读的总耗时，投影/打包、传输/调度、回读、发布、取消回收，以及主线程调用 p95/p99/最大耗时、峰值内存和显存（能测到时）。启动、稳态和释放分别记录；重复试验及结果分布不只挑最快一次。
- 选择自动 GPU 的初步参考是大范围真实负载的完整场计算中位数至少比 CPU 快 2 倍，并且主线程成本、内存和小范围表现可接受；这个数字是工程取舍目标，不是用户承诺或失败时篡改数据的理由。实测不占优就维持 CPU 默认，保留结果和原因。
- 参考 A2a 的主线程单次推进 p99 约 4 ms 目标，记录实际最大值；这不是硬实时保证。1024 次热读 p95 约 10 ms 仍是已知问题，GPU 计算本身不保证解决，本包不因此无依据扩做整套查询优化。
- 隔离基准不能冒充普通游戏 FPS。若本包增加可见开发界面，则额外实机观察并测画面；只改变开发计算接口时，以原生 GPU 测试和计时为准。16 GB 整机的全系统联合验收留到实际接管后。

## 到哪里停止

交付可复用的真实来源 CPU/GPU 接口、过期与回收保护、定向正确性和真实负载的性能报告，再停下来讨论。普通游戏是否加速要到以后接入时实测。

随后才排：原物变动与实际温度/五行响应的共同时间和原子提交；再考虑移动携源尾迹、普通 Main 切换和房间。它们不是本包完成的事实。四份受保护的未提交环境 WIP 继续原样保留，本包计划只修改真实缓存接缝、运行层调度和相应测试/基准。
