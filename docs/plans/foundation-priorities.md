# 模拟执行架构重构计划

这是唯一实施计划。当前授权和停点看[HANDOFF](../status/handoff.md)，逻辑领域看[职责](../engineering/architecture/05-framework-domains.md)，目标结构看[执行规格](../specs/world-engine/execution.md)。现有class、schema、测试和已投入工作都允许替换。

## 第一目标：游戏实际跑得动

在[目标PC](../engineering/constraints.md#产品与技术范围)上，300个持续行动人物与建筑、植物、环境、近远区共同运行，保持1×世界流速与稳定60FPS。允许大范围重写和暂时破坏旧功能；优先证明可扩展的运行路径，再恢复内容。计算不足可平滑降速，但不能静默丢时间或改因果。

实际进展、CPU/GPU采用范围和测量只查[BASELINE](../status/baseline.md)，本页不复制结果或声称目标已达到。

## 先解决哪些成本

| 范围 | 已知线索及要回答的问题 |
|---|---|
| 数据和共同运行 | 同步准备、状态发布、动态字典、重复扫描和全体补算分别花多少；原状态能否直接以热批数据运行，避免搬进worker又逐条搬回 |
| 空间和单位行动 | 已测旧寻路通行查询大量重复；地块数据、路径候选、局部避让和身体执行能否共用局部结果，避免每次调用穿过整条领域链 |
| 环境和自然过程 | 背景、房间、来源和受体是否需要相同粒度；哪些局部变化被放大成全局工作，哪些密集数学真正适合GPU且端到端有收益 |
| 呈现和生命周期 | 画面/UI是否触发模拟补算或重复复制；初始化、存读、取消和对象更替是否让热索引/任务长期增长 |

这些是调查范围，按实测最大成本选择，不逐项建设独立优化模块。CPU多核、Godot原生算法、GPU、数据布局和适当简化都可采用；不为了“使用GPU/多线程”增加比原计算更贵的准备和同步。

## 仍按顶层框架交付

| 包 | 能力与出口 |
|---|---|
| A：共同运行与热数据 | NPC移动/搬运链的数据、工作选择和批量采用重构；以实际主线程成本下降判断，现有接缝可替换 |
| B：空间、行动和自主执行 | 局部空间数据、导航、活动动作和必要决策协同；分散/拥挤和多目标下测增长。依赖共同数据接口，不等空平台全部建完才检查最大热点 |
| C：环境与自然过程 | 按实际影响范围组织计算，普通Main真实采用CPU/GPU结果，含设备回退；依据准备、传输、计算和发布总成本选择设备 |
| D：呈现、存读和可玩整合 | 视图读已提交结果，关键操作可用，整合达到300人目标；删除被替换的旧运行链，避免长期维护两套模型 |

已确认的身体/原物归属、共同时间、可中断行动和有限认识继续是游戏方向；内部表示和算法不冻结。大改引入的具体行为变化说清楚即可，不为旧功能永久保留复杂兼容链。

## 开发节奏与采用标准

按[开发循环](../engineering/workflow/testing.md)做有界测量与相关短检查，以普通运行链路的整体改善决定是否采用。无可信收益就重新选择数据、粒度、算法或后端；本计划中的实现候选可以推翻，不因已有接口继续低收益小修。

完整战斗、超凡玩法和正式内容在可扩展底座上继续建设，产品方向见[roadmap](roadmap.md)。本页不再生成额外的小算法计划或重复的测试优化队列。
