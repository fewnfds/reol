# 当前实施计划

当前授权和接续见[HANDOFF](../status/handoff.md)，实际能力与测量见[FEATURES](../status/features.md)、[BASELINE](../status/baseline.md)。本页安排工作，不重复解释接口或登记实验日志。

## 当前：试玩反馈收尾，随后统一操作系统

已有可单独启动的功能导览，集中现有能力与少量预置样本。入口及体验内容归[功能试游](../engineering/tooling/usage.md#功能试游)；具体玩法范围仍由FEATURES各领域说明，不新建另一份功能总表。

本轮先补固定物的迷雾记忆、扩大视野与远缩放、修复运行中点击失效；五行逐秒变化的来源与当前响应机制归[环境合同](../engineering/world-environment-contract.md#时间变化与受体)。实现与证据见BASELINE，不将这些局部修复再分成独立长期计划。

### 下一阶段：输入、选择与指令

目标是形成一套可玩、可扩展的操作流程，让日常行走、交互和交锋共用命令入口。以下为待实施计划；当前可用键位仍只查[操作](../status/features/controls.md)，本轮没有提前启用右键移动、A/S/H。

默认采用鼠标指令控制当前化身。**观察目标**与**发令对象**分开：左键可以检查NPC、家具或草木，但不会因此接管它；移动命令默认交给当前化身。以后可指挥的同伴须先具有真实控制/合作权限，再扩展多选，不将全体居民变成RTS单位。

| 输入 | 计划行为 |
|---|---|
| 普通模式左键 | 只选择目标；空地取消选择。框选、Shift增减选择在确有可控小队时接入 |
| 普通模式右键地点 | 寻路前往；显示受理地点与到达/失败结果 |
| 右键单位 | 第一版走到可接近的位置；后续按已知关系和能力解析攻击、交互或跟随，不能将中立目标静默判作敌人 |
| A，再左键地点/敌人 | 地点为攻击移动：沿途搜索合法敌人、交战后继续原目的地；敌人为指定攻击。A不是范围伤害按钮 |
| S | 停止移动及当前可中断行动，清理尚未执行的后续命令；已发生消耗、已经飞出的效果沿原领域继续。停止后可按正常姿态应敌 |
| H | 驻守原位置，取消追击，只攻击自身射程内合法目标；不等同于格挡、无敌或自动追敌 |
| Esc / 预览时右键 | 先取消尚未提交的目标/技能预览，再按界面层次收起面板；不连带发出移动命令 |
| Q/W/E/R、D、F、I | 分别作为准备技能、身法、镜头跟随、物品入口的首选映射；具体技能仍需实际学会和装备 |
| Shift + 命令 | 后续加入有限队列；提交时反馈队列，执行时重新验证路径、目标与资源 |
| P、跟随/保护/撤退 | 基础流程稳定且有适用执行者后再补巡逻及小队命令，不先扩成全宗门调度器 |

键位重构与命令落地同时进行：现有WASD中的A/S和新命令冲突，默认鼠标模式会释放WASD；Shift闪身移到独立动作键，给队列修饰留位；F用于镜头，不兼任技能。雀身F落地/E啄食等身份动作迁入对应技能/交互槽，镜头键保持一致。数字编组与现有速度快捷键也有冲突，编组留待小队阶段统一处理，时间控制可继续使用HUD。若以后提供直接控制模式，应显式切换整套上下文，不让一次按键同时走路和发令。

按三个交付块推进：

1. **选择与移动闭环**：将Godot命名InputMap动作、UI/施工/普通地图上下文及命令路由收拢；复用现有输入缓冲、共同时间和路径执行器，完成左选、右移、停止、目标预览取消和明确的命令回执。UI点击、暂停下令、运行中下令、目标消失和不可达都能观察到结果。无需另建世界步进、人物位置或第二套寻路。
2. **战斗指令与姿态**：在原交锋/动作框架上实现指定攻击、攻击移动和驻守，定义遇敌、丢失视野、目标死亡、受阻、追击上限与恢复原移动的关系；目标搜索使用原空间候选/CPU批适配，动画只消费结果。日常工作被打断时交回原预约与资源所有者，S/H不直接清空原物。
3. **便利操作与扩展**：按实际体验加入Shift队列、快捷施法/普通施法选择、命令列表与少量重绑；有真实小队权限后才做框选、编组、跟随/保护/巡逻。先保证单一化身和生活交互能顺畅使用，再扩大操作范围。

参考的是成熟产品的操作语义，不声称拿到了其内部代码：[Warcraft III Unit Commands](https://classic.battle.net/war3/basics/unitcommands.shtml)区分Move、Attack、Stop和Hold；[StarCraft II Basic Unit Controls](https://news.blizzard.com/en-us/article/4552956/game-guide-basic-unit-controls)与[Special Control](https://news.blizzard.com/en-us/article/4552955/game-guide-special-control)提供选择、队列与编组参考。LoL的单一英雄/技能目标体验用于取舍，不照搬其经济或角色权限。

## 已交付基础：计算接入与项目记忆整顿

用户要求在已有CPU/GPU底座上提升代码质量与可接续性，不启动新一轮容量攻坚，也不建立每个新功能必须实现的万能接口。

| 交付 | 范围 |
|---|---|
| 清晰的接入选择 | 复用直接领域逻辑、事件/分频、CPU批与现有GPU场；适用范围和示例只维护在[计算接入](../engineering/execution-batches.md) |
| 减少扩展耦合 | 分开人物需求与运动读取；自定义需求保留原顺序计算，仍可利用无关的运动候选/边界批；诊断显示具体退化范围 |
| 收敛文档与证据 | 合并重复执行规格，删除过时的任务/候选关系；基线保留有效摘要，旧测量归档；参数以代码为准，命令只在usage解释 |
| 收尾 | 原规则和特殊回调的串并行状态对照、普通会话和短实机窗口已核对，证据归BASELINE；代码与文档一同提交main |

本轮不要求任何新领域先实现批执行、GPU后端或特定基类。发现真实公共责任时才提取机制，局部低频逻辑可以保持简单。

## 多核容量优化：暂不恢复

上一轮执行底座和数百人短窗已有改善；容量工作暂缓，不把整个多核目标标为完成。当前以试玩与操作系统为主，不继续扩大并发或重跑容量矩阵。

保留的未完成问题：下一边界选择/采用和有序空间通知成本、人物显示年龄、旧UI/画布的完整世界交接、压力驱动的真实动作/社会事件成本。千人以上负载仍过载，具体证据见BASELINE；未覆盖完整战斗、长期运行和目标整机。若以后恢复，仍使用本页安排，先根据当时可玩负载重新排序。

本页之外的新功能范围由后续讨论决定。七个领域只查[职责表](../engineering/architecture/05-framework-domains.md)，长期游戏层次查[roadmap](roadmap.md)；研究和归档中的旧待办不自动恢复。
