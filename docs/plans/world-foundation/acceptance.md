# 世界骨架联合验收与性能参考

本页为[目录所列框架模块](README.md)提供联合验证和负载参考，旧阶段称呼用于定位。顶层交付按[基础建设计划](../foundation-priorities.md)的框架出口判断，结果和版本写入对应QA与[基线](../../status/baseline.md)；没有完成的测试保持待验，不把孤立脚本当产品结果。

## 可复用性与真实性

1. 同一外部查询合同覆盖真实的人身、至少一种非人或自然来源、独特物、库存材料和实际多格占地对象。各域给出原身份、位置/占地、所有者和时间信息；当前资源点和大型身体不能被描述成完整植物或通用建筑。
2. 通过定义增加一个使用已有能力的新对象；无需按特定对象名称增加处理分支。新能力可以按领域扩展一次，再被多类定义复用，不要求所有对象拥有同一组属性。
3. 对象不存在、引用无效、域未接入、能力不支持、来源滞后、世界欠算、查询预算耗尽和完整空结果可区分；返回投影的修改不能反写原世界，查询不能顺带推进时间或生成物品。
4. 同类相容物品合堆时数量守恒；不可相容实例保留独立状态。生成、转移、移除、失败、重试及中断后不复制或隐式删除事实，空间覆盖同一实体不会生成多个实体。
5. 至少一条真实联合链：从定义和开局装配 → 产生不同类对象 → 修改位置或容器 → 推进共同时间 → 离场与返回 → 保存并完全退出 → 独立进程加载 → 再推进。比较共同时间、原引用、位置、数量及在途事实；加载候选损坏或引用错误时活世界保持不变。
6. 玩家视图通过观察/认知过滤；开发侧空间查询和调试信息不得直接泄露未发现对象或远区即时事实。

上述是世界骨架模块的联合验证范围；只读查询、局部索引或定向测试只证明自身范围。通过本页检查还须按所属框架核对其余公共能力和跨域出口，不能直接宣布所有框架完成。

## 基准场景和边界

性能目标统一引用[全项目性能基线](../../engineering/architecture.md#全项目性能基线)，不在阶段页另设整机规格。每次基准先记录代码完整 SHA、未提交差异、内容与地图 seed、Godot 与系统版本、CPU、实际使用的单张 GPU 型号/可用显存、整机物理内存及测试开始前可用量、运行模式、是否渲染、测试器及输入。记录是否预热、样本数、对象类型与分布；同一种负载至少比较“无变更、局部改变和批量改变”，不要将只测初始化与真实运行帧时混在一起。

| 负载 | 必须说明和测量 |
|---|---|
| 静态对象 | 分别测 64²、128²、256²，阶段终点测 512² 每格至少一份实际对象/堆事实（262144 位置）。统计真正对象及来源种类、占格数量；不能用空地图或只有图标代替。静态不逐帧调用对象脚本。 |
| 动态对象 | 在同一世界独立递增活动身体和移动/占地更新数量。记录每秒变化频率、跨块比例与路径调用；静态密度数不等于这么多 NPC。 |
| 来源与五行 | 来源密度、半径和变更比例单列。第一阶段仅测可承载和检索相关引用；冷热/五行传播和 GPU 是否加速由后续环境包单独验收。 |
| 跨域与内容 | 同类与不同类型混合、每堆数量为 1/4/16/10000 的数量投影、局部移动、容器变化、多格及跨块；记录查询预算用尽与过期重试。 |
| 保存和远近区 | 已完成和在途存档各测，记录写入、校验、加载、恢复索引耗时与峰值；声明远区推进的实际覆盖范围。 |
| 共同结算与持续运行 | 声明默认预算、活动过程及同时到期数量，记录实际模拟毫秒/现实秒、积压增长与消退、一次完整边界延迟、最慢原子步骤、命令/保存等待。长局另记模拟时长、库存operations及认识events数量、内存/存档体积/恢复时间的变化；短开局帧时不能替代。 |
| 扩大探测 | 1024²、2048² 作为后续递增探测，不凭地图尺寸或合成索引成功宣称普通世界扩容。首次超限后记录并停测。 |

稠密压测应尽量走正常装配与原所有者。必要时先做合成结构样本来测算法，但必须单列其内存与功能边界，不能把单独索引中 262144 条引用当作 262144 个已持久化、可交互对象。

限工作量可以保护响应，但若积压持续增加、普通操作长期被拒绝或保存一直无法完成，该负载仍不能交付。记录稳定帧时与世界实际推进速度的关系；在原owner确认幂等/责任/知识引用的保留条件前，不以删除历史换取通过。后续近似须先声明保留的因果、不变量及误差，再比较完整推进，不用离屏停算代替远区规则。

每条负载至少记录：初始化总耗时；单次及批量查询、局部变更和重建的工作量/耗时；模拟阶段耗时；保存和加载耗时；整机可用物理内存低点，以及进程工作集、私有内存和提交量峰值；实际渲染测量的帧时 p50/p95/p99。GPU 若参与，还需单列实际使用设备、构建、上传、设备计算、读回、发布和该设备专用显存峰值；共享系统内存若被使用则另行记录，不与独立显存相加。结果还需与 CPU 正确性合同比较。

## 试验门槛与安全上限

以下是首轮工程目标，具体硬件与场景必须随报告给出；不是已经达到的性能承诺，也不将某台机器的结果泛化到所有配置。

- 在项目采用的本机桌面硬件与声明的 512² 负载上，视图预热后采集不少于 1800 个连续帧：目标帧时 p95 ≤ 16.7 ms、p99 ≤ 33.3 ms。必须同时报告活动对象数、可见对象数和实际地图/对象渲染情况；未达标不能宣布该负载的目标通过。
- 对静止与局部变更分别记录真实模拟耗时和内存，明确局部变更规模；静止时不得因为全图静态对象数而逐帧逐个执行对象逻辑。大范围查询可以受预算约束，但预算不足必须可续算或显式失败。
- 每次压力测试前按当时可用物理内存、已有进程占用、测试负载和该设备的可用显存预先设定有限超时与内存守卫，为系统及其他进程留足余量；不再把 30 秒、1 GiB 当作固定验收门槛。测试期间监测整机与被测进程内存，GPU 负载同步监测对应设备显存；达到所设守卫即安全终止并报告上限、原因及已完成规模。不得并发压力任务，也不得为了跑完而绕过守卫或损害其他进程。
- 首次资源导入、完整项目回归与数据结构压测是不同负载，各自预设合理的时间和资源上限并记录实际峰值；不得为满足临时守卫删图或修改产品。导入失败先处理首错，不能继续把资源缺失后的连锁失败当框架结论。
- 使用共同时间分段推进的操作要比较整段与分段结果；包含保存重启或候选被打断后重试的测试，结果保持一致或提供明确误差合同。近似策略须记录允许误差和适用范围。

如果上述目标未达，先定位实际热点并保留报告；调整临时测试守卫不得改变正确性要求、对象数量或验收负载。调整性能目标必须写明依据和影响，不能放宽断言或只换一个负载凑通过。与旧版本的比较要求同硬件、相同负载、同测量范围，不能把不同口径的数字直接做倍率结论。

## 每包证据

- 相关定向验证覆盖成功、失败、时间/归属边界；存读修改覆盖声明支持的输入、进行中与独立进程。
- 一次适当的完整回归由项目规则所要求的本机 check 或对应完整 SHA 的 CI 证明；排队和旧 SHA 绿色不是当前通过。
- 涉及可见内容才实机观察画面；无头结果只能证明规则和离线负载。原测试 fixture、截图、日志不被改写。
- 每包记录范围、真实结果、已知限制、性能及接续；只在全部阶段出口有证据时更新阶段完成状态。
