# E3-a：野药、有限水与真实照料

2026-11-03，**E3-a有限包已实现，定向、真实进行中完整停开和完整check已验证**，见[QA](../../qa/20261103_herb_ecology.md)。本文承接[环境总方案](../../../design/proposals/environment.md)的E3，交付一种植物与原生活的可玩因果链；持久地形修改留给E3后续包。最新构建与功能范围只看[BASELINE](../../status/baseline.md)、[FEATURES](../../status/features.md)。不是完整生态、E3全部完成或完整游戏验收。

目标：天气和温度真实改变药草供给，照料有原水、工时与机会成本，采得实物能进入现有救护、加工和交易。
体验：玩家能选择携水照料、等雨等暖、另寻现有货源，以及把有限鲜药用于自己、他人或谋生。
约束：同一世界时间、原cell/来源身份、原库存、原身体/路线和有限认识；近区与远区执行同一规则，不因到场重生资源。
已验链路：缺水/寒冷/降雨定向、原私水照料→同源真实采药→原私料焙药/取成品→离场，含进行中真实档完整重启。原鲜药救护/有限交易保留，不将这次采药焙药证据写成新完成整套医疗或市场。

## 1. 从已有药源接一条生活链

两地原`herb_slope`均由各自`SimLandResources`登记，成熟药草只在原`resource:herb_slope`容器中。原`gather_herb`、`keep_herb`已包含来源预约、行路、劳动和真正采出；前者交公库，后者留本人行囊。原鲜药处理和私料烘药/有限交易提供实际去处，见[身体后果/救护](health_and_recovery.md)、[私料加工](personal_production.md)。

首包把这些来源解释为固定地点的一丛多年生野药，加入土水、生长与休眠过程。不是为世界各格自动生成植株，也不是把药源改成无限点击奖励。两地分别拥有过程，使用同一规则；先前采空、人物在途携药和库内存量保持原来源。

玩家至少能做两种应对：以本人可处分的水实际浇灌，或等待真实降雨与适温时段。已有采药NPC继续访问同一受环境影响的来源，因此缺料和劳动会有实际后果；首包不承诺NPC自主寻找最优农务计划。

## 2. 空间、认识和交互边界

药丛使用原`region + source_id`稳定引用，位置从原来源所挂`place.cell`取得。它仍处在原世界cell，不能因一幅植物图增加第二份位置、地块或库存。近旁可画一丛简易植物，卸载图像只卸载视图。首包不引入新的Entity/ECS平台、不改变人物连续移动，也不实现植物自我扮演、出生或转生。

该单格地点/来源锚点是此野药样本的当前边界，不是药田必须只占一格的设计；可框选种植区域、多格植物和温室均尚未实现。长期合同见[建造与空间](../../../design/systems/construction_and_space.md)。

附近观察沿原可见/距离条件，给出“土面发干”“叶片卷曲”“寒中歇长”“有嫩叶可采”等对应线索；远处只保留来源位置与原先所知，不展示实时土水、成熟倒计时或后台温度窗口。描述应区分看见、推测和既有记忆，不能看到叶蔫就免费鉴定全部原因。

照料和采药仍按动作、对象、条件补全表达，无AI也可完成。开始前可以说明本人已知的缺水/道路/材料问题；涉及未观察事实的失败应提供当场可知反馈，不远读NPC行囊或植物真值。首包不因此加入通用对话、自动传闻或共享生态知识库。

## 3. 唯一状态所有者与增长规则

原`SimLandResources`已持有受管药源生态状态，`SimHerbEcologyRules`负责纯积分、定义和局部状态校验。父级只驱动环境采样与同步，不拥有第二份植物数量或另走一条时钟。

| 事实 | 唯一所有者/接续方式 |
|---|---|
| 成熟可采药草、行囊鲜药和可处分的水 | 原`SimInventory`容器、预约与操作记录 |
| 来源产出/采出累计及原库存守恒 | 原`SimLandResources`，采出仍反查原`:harvest`操作 |
| 启用时刻、土壤有限水、输入/流失累计、生长进度及整数余数 | 该来源的新增生态状态，不保存第二份成熟药草量 |
| 环境采样时刻、当段温度/降雨条件与规则版本 | 该来源过程的缓存；恢复后继续旧缓存，不能重采覆盖旧段 |
| 携水、行动占用、路线、劳动和取消 | 原人物`active`、执行器、身体与库存预约 |
| 晴雨/地区气候、固定空间余热 | 原weather/climate/local_heat；植物不拥有这些来源 |
| 图像、可知描述和界面选择 | 只读投影，不提交生长或生成物资 |

仅受管野药改用新过程。**其原固定周期增长必须停用**；同一药源不能一边按旧两小时规则长药，一边按新生态再长一份。其他来源暂保留原行为。

适温且土水达到湿润恢复条件才能积累生长；寒冷休眠或缺水停长，恢复后接续已有进度。低水量采用干湿滞回，微弱雨水不会每毫秒反复唤醒增长。采用植物自身温度窗口，不套人类衣位、舒适度或精力负担。温度来自原地理气候与同格已支持的局地余热，不能凭空把某人携带温石视为持续植物热源。

完成生长时，新增成熟药草只提交到原来源容器，同时更新原`produced`依据。库存满后不储存无限错过的成熟产量；采空也不删除药丛。首包不腐坏已成熟/已预约药草、不引入植株死亡，因此不能用新增生态悄悄打破原采集预约。

土水使用有界整数微量，生长进度是实际吸收水的整数工作量，不通过浮点比例舍入成产量；不能用“浇水次数”永久加速。当前定义为原一份水转换60000000微量、土水容量180000000、启用土水36000000、恢复阈值6000000，5–35°C内适水生长；全部仍是可调游戏参数。满足：

```text
当前土水 = 启用初始土水 + 有来源降雨 + 实际浇入
           - 蒸散 - 生长吸收 - 溢流
原成熟库存 = 原initial + 原produced + 原rainfall - 原extracted
```

药丛降雨输入与原泉源收雨分别按各自实际地点/面积定义上界，不能把泉源已有水或其`rainfall`累计再当成药丛免费雨水。新增土水不允许反向提取为行囊水。过湿溢流必须记去向，不能负水、越容量或静默删除差额。生长率、温度窗口、土水容量、降雨/蒸散/吸收率、一次照料水量与工时放`data/definitions/`，通过场景测试定参。

## 4. 父级分钟采样，旧缓存只影响其后区间

首包采用**每世界分钟一次父级采样**，结合原动作及生长/土水阈值边界积分，不按帧、不按查询次数增长。`VillageSimulation.advance_to_ms`在父级提交新时间前就推进来源，来源内部不得为查未来条件而回调、推进世界environment或local_heat。

在共同边界T采用以下顺序：

1. 原来源按已保存旧环境缓存将上一段过程结算到T，先处理旧段成长、蒸散/吸收与到达的成熟/耗尽阈值。土水改变处须切段，不能用区间末尾一份水为整段补算生长。
2. 照料、采出、原热作用及结构变化各自先结其旧过程，再在T提交真实作用。同刻顺序固定，不能以不同地区或字典遍历顺序决定谁多取物资。
3. 父级采样前将相关原地区同步到T，保证原人物动作和来源旧段均已结清；再读取T已提交的晴雨、地理温度与同格余热，保存未来环境缓存。
4. 新缓存只用于T以后的区间。两次采样间气候/热条件改变最多延迟一个采样间隔生效，不倒算先前生长；同刻浇水应先结旧段再入土，不能为过去补水。

植物过程用定点整数与持久余数；在土水用尽、达到容量、成熟和满库存处有确定处理，细步、批步、预算分段不能改变产量。只读观察/投影不能推进真值。若纯投影不支持某种将来条件，不能用“预测成功”代替实际成熟或扣水。

父级采样允许首包逐分钟同步**两个已登记药源所在地区**；不用每格节点或扫描整张地图，也不因玩家远离就停采样。此方案可能使这些地区更频繁同步，是明确的当前规模限制；不宣称已能高效推演多年、多大陆或海量植物。预算耗尽保留欠算，不丢世界时间、不漏环境输入。

## 5. 实际照料与原子水账

首包照料采用原人身劳动的新有限动作类型：本人已有可处分水→预约→沿原路线到药丛→花原工时→完成时入土。它不是远程施法，不直接从泉、仓库或别人行囊跨空间取水。

开始时验证原动作/移动控制、身体可用、目标和可达路线，预约本人实际可处分的水。受托公物沿原custody限制，不能借照料无声侵占；新的公共取水授权不在本包内。劳动沿原精力消耗，不能边远行、诊治、施工又完成同一身体照料。

完成时先同步来源到该时刻，并对行动、到场条件、原预约、水的处分权和土水上界做完整预检。原库存`consume`与土水接收使用同一动作来源ID，在无`yield/await`的提交段内一次落地；如需要候选，先在候选核验全部影响再共同提交。不得先扣真水再发现土水候选无效，也不得先加土水而未扣真水。重复settle只承认同一笔，不重复消耗或灌入。

开始前已湿透可以拒绝无必要照料；开始后因雨水改变容量，则按完成时条件把入水分成留土与有记录的溢流，并给当场可知反馈，不能复制退款或吞掉未记录差额。完成前取消/失去控制/路断释放未用预约，不产生照料效果；已耗工时与原精力不返还。完成后不再以取消撤销既成扣水或自然流失。

照料首包贡献为零，不能同时产生免费公差贡献或工资；实际成果仍是后续可采药草。原通用“去功德堂登记”提示须按动作语义处理，不给玩家错误承诺。

## 6. 旧档启用与候选验证

本包采用根33、区域29、村落6、来源3、生态规则/状态1，最新格式仍以BASELINE为准。新增动作采用明确开局配置迁移，未把整个旧配置替换成当前配置来掩盖本应拒绝的差异。真正没有来源的早期世界不补造药丛、照料动作或过去雨水。

旧档在原保存时刻启用植物生态。保留原药草库存、历史产出/采出、来源身份、泉水与收雨、人物在途路线/预约、原公私物及温石状态。新增初始土水需有明确的当前启用策略并持久记录，不追补过去降雨、成熟、枯萎或收益；新局按开局定义初始化，已启用来源重开不得重新领一次初始水。

启用时先登记当前环境为未来缓存，不结启用前过程；首个新的父级采样采用“启用满一分钟后的首全局分钟边界”，与原环境启用边界一致。期间实际照料仍只从它自身的真实完成时刻生效。保存并恢复采样时刻、积分进度及余数，不根据读档时的季节/现房屋重采过去。

原校验中的固定周期产出上界不能直接套生态产量：分开保留启用前已合法固定增长基准与启用后的生态产出依据，再核对同一原来源守恒。灌入累计反查原水consume操作及双方引用；降雨受真实已过雨段上界约束；土水、余数、阶段、来源覆盖和时刻要严格验证。不能只信候选写了“浇过三次”。

局部土水/生长/原库存与灌水凭证先独立校验，父级再核真实地理气候、晴雨持段上界与原热历史采样。全部独立候选通过后才提交，任一坏引用不能部分修改当前人物、库存、来源或世界时间。候选初始化保持真正开局时间，完整restore再提供保存时刻；不只移动候选村钟、把零时土水错配到未来。真实旧fixtures和用户源档只读，不通过重存全部历史档让新校验“变绿”。JSON读入后的已校验生态整数在绑定时规范化，避免重复读写改变时间上限和大整数。

## 9. 非目标与后续接口

本包不实现全地形编辑/持久地表delta、引水工程/完整水循环、种子播种/繁殖/物种竞争、植株死亡/腐坏、完整农业产业、土地产权/公共照料授权、NPC通用农务规划、五行灵源/风水或植物自我扮演。原`construction.protected_cell`仍保护garden等原place格，因此不承诺能直接在药源同格盖棚；温室和改造用地须后包补实际空间/施工接缝。

本包只给P1生计和P3救护已有链增加真实环境约束，为后续创造/修行留下同一来源与空间接口；不代表P1–P4全部完成、E3全部完成或45–60分钟切片已验收。完整阶段出口继续见[长期计划](../../plans/product/full-game.md)、[验收矩阵](../../plans/product/acceptance.md)与[路线](../../plans/roadmap.md)。
