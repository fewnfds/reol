## 1. 目标与验收方向

构建一个持续运转的修仙社会：人物各有生活、目标和个性，组织依赖具体条件存续；玩家以不同身份进入，都能遇到与自身处境有关的选择。

玩家通过生活、合作、修炼、冒险和组织活动取得资源与地位，又受到他人的目标、信息、权力和环境变化影响。关系、声望和贡献有各自来源与作用。

初次验证：沿用现有 5 名 NPC 和首区，让他们自行完成日常工作，并围绕一次真实的资源短缺形成求助、回应、履约和后续影响。玩家可参与，也可旁观。此后再逐步增加制度、争议和权力更替。

验收始终关注三件事：无人操作时仍能运转；改变资源、历史或认知能改变选择；玩家能通过实际渠道逐步理解原因并采取行动。

## 2. 六个协作部分

以下是职责划分，不对应六个必须立即创建的 autoload。

| 部分 | 管什么 | 在游戏中表现为什么 |
|---|---|---|
| **世界状态** | 地点、身体、物资、设施、在场人物、生产与消耗 | 谁在哪里、有什么、能到哪里、东西是否真的存在 |
| **人物行动** | 需要、职责、目标、选择、互动、承诺、工作执行 | 吃饭、修炼、求助、接受、拒绝、代工、交易、争斗 |
| **信息与关系** | 观察、通信、信念、记忆、交往历史与领域评价 | 谁认识你、谁听说了什么、谁相信你、怎样传成名声 |
| **组织与制度** | 成员、职位、规则、授权、账目、共同资源和组织决策 | 谁能下令、谁记账、谁审批、谁执行、违规如何处理 |
| **局势演化** | 持续的问题、机会、环境变化、期限和长期结算 | 缺粮、欠账、人员短缺、争议、继任、外部竞争 |
| **玩家呈现** | 操作、对话、观察、日志、可见解释及不同身份入口 | 参与这张社会网络，并理解自身处境与行动后果 |

共同流程：

```mermaid
flowchart LR
    A[需要、职责或环境变化] --> B[人物根据所知选择]
    B --> C[交互与实际行动]
    C --> D[身体、物资、职位等发生变化]
    D --> E[参与、观察、通信、登记]
    E --> F[形成认知、关系、记录与新目标]
    F --> B
    D --> A
```

战斗、修炼、生产、探索是具体行动领域：它们读取、改变同一个世界状态，并进入同一条社会后果链。受伤会减少劳力，突破会改变机会与风险，稀缺药材会引发采购与竞争。

## 3. 世界状态：先让行动有真实代价

每个持久对象使用稳定 ID，位置、数量、伤势等由唯一状态负责。画面中的节点只是其在当前区域的表现。

物资至少区分数量、所在容器/地点、实际保管与预约。所有权属于某种被主张或认可的社会关系，不等于实际持有：库房被盗后，宗门仍可能主张所有权。

生产必须有输入、耗时和产出；取食会消耗食物；送药需要取出、运送和交付。初始储备与自然补充有明确来源，交易只是转移，不能因为交任务而凭空生成无限报酬。

第一轮只做一条短供给链，例如“粮食、水、柴→灶房做饭→人物取食”，加休息与有限职责。无需先模拟完整生态和市场。

资源预约防止两人同时花掉最后一份材料；接受提议不等于已经拿到材料。行动取消、目标消失、死亡或不可达时，释放预约并产生明确失败原因。

## 4. 人物行动：目标、选择与执行分开

### 人物的最小构成

| 信息 | 用途与边界 |
|---|---|
| 身体与能力 | 伤势、饱食、疲劳、修为、技能；决定实际能力与部分需要 |
| 身份与职责 | 多重成员身份、职位、师徒等关系；规定日常责任与可争取的机会 |
| 少量价值偏好 | 守诺、关心亲友、求知、逐利、重名等；选相关偏好，不铺设完整人格量表 |
| 当前目标与计划 | 生活、工作、修炼、照顾他人等目标；同时激活少量目标，已有计划保持一定稳定性 |
| 已知信息与历史 | 自己观察、收到或记住的内容；允许错误与缺失 |
| 正在承担的承诺 | 为谁做什么、期限、条件、责任与履约状态 |

玩家选择自己的行动，NPC 通过规则选择；两者共用动作的成本、执行和后果。同一种药不能给玩家与 NPC 两套库存。人物是否由玩家控制不构成额外的社会权利。

修为能力、宗门成员身份和具体职务分别表达。外门弟子是成员层级，管事是办事职责，境界是能力与成长条件；它们可以互相约束，但不合并成一条万能等级。迁移现有 `RankDef` 时逐项核对，不仅改显示名称。

### 决策方式

日常职责与习惯先形成稳定计划，重要变化才触发重评。根据人物所知，生成少量可考虑的方案，再结合目标、代价、人际经历、规范、权力情境和个性评估。

选择阶段读取人物认为的机会；执行阶段检查实际条件。人物可以误以为库房有药而答应，取药时才发现缺货。不能把引擎已知的秘密提前用于 NPC 决策。

先用简单效用评估加有限随机性；强烈倾向与确定的职责直接处理，接近的方案才需要骰判。参数通过场景校准，不声称是科学预测人类的公式。

相同处境和条款下不重复抽取同一提议的结果。保存议题对应的互动、决定与随机状态；只有代价、条款、证据、时机等有效条件改变，才重新评估有关选项。重复请求通常沿用已有决定，施压可引发烦躁或拒绝交谈；换一个事件 ID 不自动取得新骰判。防止行动频繁切换，也防止玩家靠重复点击刷成功。

### 交互和工作

交互实例保存参与者、事项、条款、回应、承诺、期限和当前进度：

`提出 → 回应/提条件 → 达成或结束 → 实际执行 → 交付与结算 → 留下后果`

搬运、取食等动作由简单执行状态机完成：移动、取用、等待、交付；以后按需扩展复杂计划。先不建立通用的无限规划器或完整行为树编辑器。

NPC 之间也能发起请求。玩家管理宗门时，指令进入有权限的人发布的工作或命令；受命者是否获知、愿意服从、能否做到分别处理。既定职责不要求每搬一件东西都重新谈判或掷骰。

工作来自具体缺口或持续职责，包含发布者、验收者、材料与报酬来源。完成、验收、登记贡献、支付报酬是不同步骤；确定的小额日常流程可以连续自动办理。

## 5. 信息与关系：没有全知的社会评价

必须区分四种内容：

- **发生记录**：引擎记录发生过的事、时间、参与者与原因，供规则和开发追踪。
- **人物认知**：谁通过什么渠道获知、相信到什么程度、是否仍记得；可能与事实不符。
- **机构记录**：有权限者通过登记流程形成的账页、批文或法器记录；也可能错误、损毁或被篡改。
- **玩家笔记**：玩家掌握和整理的信息；提交给某人后才进入其认知或某个程序。

引擎广播信号不等于所有 NPC 听说。消息通过参与、目击、交谈、告示、信件或法器等明确渠道传递；记下时间与来源。转述同一消息不应被自动算成许多份独立证据。

信息过滤同时约束选择与结果解释。记忆、关系和后续目标只读取面向该人物形成的观察或消息，不能直接读取完整事实日志中的秘密原因。“故意失约”与“阿禾认为对方故意失约”分别表达；看见没送柴，并不自动知道没送的原因。

人物关系有方向，可包含身份关系、关键经历、未结承诺和按事项形成的预期。亲近、能力信任、守信预期、敬重与畏惧可以共存且互相矛盾。帮助陌生人也可以出于职责或善意。

对组织、阵营、地域群体的印象影响初始判断与风险估计；直接交往、具体事项与身份关系继续发挥作用。地域是空间范围，阵营可以是联盟或身份分类，并不都拥有统一指挥者。

声望通过传播形成，可保留有来源的摘要；不让每个人永久存下所有细节。公开态度根据听众、规范和风险生成，实际付出另按具体行动评估。

## 6. 组织与制度：共同目标要有人落实

组织至少有成员、职位、资源基础、规则、当前需求和未结事务。立足之本可以是药田、功法传承、商路、保护能力或其他具体条件。

组织没有全知人格：掌门或会议根据其收到的信息作决定，执事传令，具体人物执行。部门、派系、私人关系可以改变执行选择；共同目标不会抹掉内部差异。

以下内容分开表达：

1. **规范**：什么被认为允许或应该做。
2. **授权**：谁能以何种身份代表组织作什么决定。
3. **承认**：有关人物或机构是否接受凭证、身份或主张。
4. **执行**：谁控制钥匙、物资、人员与时间，是否实际办理。

规范可以被违反，授权也可能被滥用。物理障碍或法器约束可真正阻止行动；一般门规则通过发现、举报、裁定与追责产生影响，不能都变成全知的系统禁行墙。

贡献由账本记录发行者、受益者、数额、范围、依据和状态。个人欠情留在人物历史或明确承诺中；不把所有情感都改成可流通 Claim。

任职、职位授权和私人关系分别延续。人物死亡使其无法继续行动；机构债务、私人债务、遗产和担保的后续取决于各自条款与承认。继任不是所有关系与旧账的统一清零。

现有 `SuccessionResolver` 保留为隔离的局部原型。接入时重新评审适用范围，不能让它自动代表整宗所有成员的认知和选择。

## 7. 局势演化：让事件有前因和后续

“事件”分成三类，不共用一个模糊对象：

| 类型 | 例子 | 作用 |
|---|---|---|
| 已发生的事 | 一次送药、一次拒绝、某人去世 | 留下结果与知情依据 |
| 正在发生的互动 | 求助、谈价、担保、审计 | 协调参与者的下一步选择 |
| 持续的局势 | 缺药、债务逾期、职位空缺 | 在一段时间内推动新行动与变化 |

局势有原因、关联人物与资源、期限、进展及结束条件。用少量模板组织常见问题，多种行动可以解决或恶化同一问题。具体人物只根据自己获知的情况响应。

天气、灾害、外来商旅等可以作为有来源的外部变化，带实际后果。编写剧情也可以引入人物或条件，再让共同规则处理。叙事调度主要负责呈现与节奏，不任意改写库存、关系或人物动机来凑戏。

玩家的任务日志是其接触到的承诺与局势的视图。世界里有其他人的事务，不需要每件事都等待玩家接受。

时间尺度分层：眼前行动按固定 tick/物理推进；日常按计划与变化触发；组织按议事、缺口和周期推进；远区按较粗粒度结算。

长期演化再加入人口、寿命、继任、资源兴衰、知识与记录传承。闭关百年按重要期限与周期推进，不逐分钟重放，也不仅做一次全体好感衰减。

## 8. 玩家呈现与多身份

玩家日常需要知道：我正在做什么、谁在等我、我欠了什么、有什么可争取的机会、当前障碍是什么。通过行为、对话、凭证和已知原因表达，避免要求玩家查内部参数表。

不向玩家免费公开他人全部心理和真实秘密。开发工具可看完整决策依据与因果链；游戏 UI 则受玩家获知范围约束。界面明确区分已确认、听说、猜测和待核验。

不同开局由人物、位置、物资、身份、关系、已知消息与未结事务共同构成。社会权利有相应的任职、记录或历史来源。换个身份进入仍使用同一套动作与世界规则。

初期用测试开局检验杂役、管事、散修三种处境，不要求立即制作三套专属剧情或完整角色切换功能。正式可选身份范围另随内容成熟确定。

## 9. 技术落地与复用

### 计划制定时的基座（历史；最新状态见实现记录）

- 已有区块、格坐标、通行/碰撞、迷雾和固定 tick 时钟。
- 已有 `ReolContentDB`、Origin/Rank/Pawn 定义、`PawnState`、5 个具名 NPC 和选中面板。
- 当时 NPC 仍是静态表现，需求更新、NPC 寻路、工作执行和社会互动尚未形成闭环。
- 当时 `PawnState` 仍存 `contribution` 与 `reputation`；迁移需同步处理出身、晋升、HUD、测试，避免两套余额并存。
- 当时时钟为 10 tick/秒、1 游戏分钟/tick，一天实际 144 秒；后续已改用共同整数毫秒，最新情况见[ARCHITECTURE](../../docs/engineering/architecture.md)。

### 组织方式

模拟状态与规则使用可无头运行的 GDScript 数据对象和小系统。一个模拟装配入口管理状态、调度与规则调用；场景负责近区表现、物理行动和输入适配，`main.gd` 不继续堆业务规则。只按需要增加 autoload。

静态定义留在 `data/`；运行状态可变且可序列化。使用稳定 ID，不把节点路径或共享定义对象当存档实体。

定义 ID 与实例 ID 分开：同一种弟子或物品定义可以生成多个实例；每个持久人物、承诺和需独立追踪的对象仍有唯一身份。已有具名人物 ID 可复用，但不能默认所有运行实例都由定义 ID 唯一标识。

接口概念上分为：从人物认知查询选项、提交行动意图、推进执行、提交结果、通过渠道分发消息、查询玩家可见信息。不是所有规则都通过一个允许任意改状态的通用接口。

执行提交时复查实际资源、预约、目标和适用条件；同一交付与付款有稳定操作标识，重试、读档或远近切换不得重复生效。选择时的认知错误则保留为可产生后果的行为。

近区执行器将到达、受阻、中断等结果提交到确定的模拟 tick，作为可记录的执行输入。数据模拟的确定性以相同初态、tick、指令与执行输入为前提；不承诺现场物理跨帧逐位复现。无头验证用具有行程、耗时、失败与取消语义的替代执行器，不把正式运输简化成无条件瞬移。

全局 1x/2x/4x 应一致推进移动、工作、需求和期限；建议玩家与 NPC 的世界行动同倍率，UI 与指令输入仍可响应。暂停时停止世界行动。早期玩家移动与时钟倍率未统一的接缝后来已有共同时间样本；后续新增行为仍应遵守相同合同，不能让加速只增加疲劳与违约风险。后期局部慢放再作为明确的个体修正。

存档尽早覆盖模拟状态、时钟、在途动作、待处理执行输入、承诺、认知、有效记录、预约和随机状态。用版本化快照加有限的重要历史，不要求从创世日志重放整个世界。在 tick 的一致提交点取样，将本次物资转移、预约与动作进度一起保存；读档完成引用和预约校验后才恢复推进。

物资取出后进入搬运者容器，不再计入原库存；“在途”只描述这份物资的任务状态，不复制实物。搬运者死亡时按掉落/遗留规则处理；取消工作不凭空把已搬走的物品退回库房。缺失目标与失效预约有显式清理规则。

远近切换只改变精度与表现，持久人物、资产、未结承诺和官方记录保持连续；普通背景人口后期可聚合。近区物理与远区粗算无需逐步完全相同，但不得重造身份、重复结算或泄露消息。

性能先以现有 5 NPC 和一个供给链测量。决策按相关变化/间隔触发，限制候选行动和活跃互动；避免每帧全人物两两扫描。第一目标沿用现有 60 FPS，模拟工作以实测预算约束，扩规模前再评估。

## 10. 早期开发顺序（历史建议）

以下为成文时的依赖顺序和历史阶段，不是当前待办或最新验收。实际安排见[世界引擎执行计划](../../docs/archive/specifications/world_engine_execution.md)，是否恢复实施以[HANDOFF](../../docs/status/handoff.md)和用户最新指令为准；每一轮仍应形成可验证构建。

| 轮次 | 交付 | 完成标准 |
|---|---|---|
| **A：模拟基座** | 稳定 ID 与状态归属、可推进的模拟入口、最小观察记录、快照读写；核对时间节奏 | 不依赖 UI 能推进；同初态、同 tick/指令/执行输入得到相同数据模拟结果；存读可继续 |
| **B：宗门日常** | 饱食/疲劳、日程、NPC 移动、库存/预约、取食休息与供给工作 | 5 NPC 自行生活；缺料/不可达会等待、求助或失败，不会永久卡住和重复领物 |
| **C：互相需要** | NPC 对 NPC 的请求、回应、承诺、代工、基本通信和交往解释 | 玩家旁观时也出现合作；改变代价、历史或所知能改变回应；失败产生后续选择 |
| **C+：离场与归来（首版已验证）** | 两个小聚落、区域调度、稳定区间批算、跨区运货与近区接续 | 37 组测试绿色；离场仍运行，途中返回可干预，联合存读一致；更多行为与规模待扩 |
| **D：组织办事** | 一个宗门、少量职位、功德堂账目、审批/兑付/通行；迁移人物贡献与总声望字段 | 公账有发行与办理依据；尊敬与权限可不同；晋升进入有资格、有决定者的流程 |
| **E：局势与冒险** | 短缺/误会/纠纷的持续局势，修炼与小规模战斗接入；三个身份测试入口 | 资源、伤势、关系和职责相互影响，形成 45–60 分钟可玩切片；身份不同仍能行动 |
| **F：世界规模与世代变化** | 在 C+ 连续性基础上扩大区域、人口、继任、传闻和长期演变 | 旧账、授权、记忆分别延续，长期变化留下可追踪后果；闭关仅作为例子 |

信息边界与最小存档从 A 开始，后续逐步扩展；不把它们拖到系统全部写完之后。日常工作早期使用明确的物资或职责回报，正式贡献在 D 统一迁移，期间不新增依赖人物总贡献的玩法。

### 当时的第一个开发包

按 A→B 的最短路径拆小任务，每项单独验证；只给当前需要的对象建结构。

1. 核对现有时间、人物 ID 与场景绑定，列出首条供给链和状态负责人；写下可执行验收用例。
2. 建立可无头推进的最小状态与库存转移/预约规则；验证最后一份资源不会被重复取用。
3. 接当前时钟、人物需求和一种日常动作；记录参与者知情的结果。
4. 做最小版本快照与恢复测试，覆盖未完成动作和预约，不先铺完整存档菜单。
5. 接 NPC 在近区移动与取食/休息，再加入一次取柴送柴工作；显示正在做什么和受阻原因。

之后进入 C，使同一批动作可被人物请求和承诺驱动。首个社会演示可以是：灶房缺柴，阿禾请求老周补给；老周疲惫或已有承诺，可能接受、提条件或求石头代工；石头自己的挑水职责又影响选择。结果改变做饭、取食、疲劳和后续合作。各条分支由当前状态决定，不写死人物必然拒绝或帮忙。

## 11. 必须通过的行为验证

| 场景 | 需要证明 |
|---|---|
| 无玩家输入推进若干游戏日 | 日程、生产和消费仍推进；资源耗尽有明确后果与恢复/求助路径 |
| 两人争同一份资源 | 只成功转移一次；取消、死亡、不可达释放预约 |
| 尊敬但拒绝高代价请求 | 关系不能自动替代代价、职责或其他承诺；改变条件可改变回应 |
| 善意帮助陌生人 | 有关心/职责理由时可发生，不要求所有帮助先有交易 |
| 请求未送达、意外失约、故意违约 | 留下不同事实与解释；新证据可以纠正部分误解 |
| 秘密事件与转述 | 未获知者不凭空反应；公账不是目击后自动生成 |
| 完工、记账、兑付及重复提交 | 真实交付、登记和支付各有依据；重试不能刷奖励 |
| 掌门更替 | 选定场景下可出现仍受礼遇但被拒绝通行，同时某笔公账继续有效 |
| 存读继续与远近切换 | 重要身份、状态、在途事务与随机状态连续；不重复发钱或泄露信息 |
| 同任务在 1x 与 4x 运行 | 相同行程与操作应消耗相同游戏时间和资源；快进不单独加重需求与期限 |
| 同世界的不同身份入口 | 机会、职责和风险改变，共用的动作规则保持成立 |

验证分纯逻辑、可推进的多人场景与实际游戏观察三层。每个实现任务运行 `python tools/godot.py check`；涉及表现则运行游戏、读日志并留截图。本次计划仅改文档，不把环境诊断当作新框架已通过测试。

## 12. 取舍与后续定参

先采用少量需求、偏好、目标和互动；有向关系与来源明确的信息；简单执行状态机；有限历史与版本化快照。相较单一声望，增加的成本主要换取选择和后果可解释。

完整心理模型、全面市场、所有身份剧情、完整宫廷政治和百年逐人生活都不作为第一个构建的前置条件。先用同一批规则形成可玩的局面，再按验证暴露的问题扩展。

具体需通过后续试玩确定：昼夜比例、生活压力、候选行动数量、骰判曲线、传闻频率、记忆保留与 UI 暴露程度。用户可继续用场景和期望行为引导，我负责把反馈转成规则、实现任务和测试；不要求用户先命名类或设计接口。
