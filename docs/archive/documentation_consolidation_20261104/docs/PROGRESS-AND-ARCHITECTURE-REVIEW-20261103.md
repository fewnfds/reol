## 4. 当前架构是否合理

结论：**模块化单体的方向合理，适合继续做切片；当前接线方式尚不足以低成本扩成完整大世界。应渐进整理反复接缝，不全面重写。**

值得保留：

- `sim`、`runtime`、显示与文件读写分离；卸载画面不销毁世界事实。
- 共同整数时间、明确边界及稳定顺序；没有为每种新玩法另造时钟。
- 同一身体、库存和器物被多个用途竞争，而非每个系统免费复制资源。
- 本人认识与真实事实、个人好感与机构权限分开，是社会特色的有效基础。
- 独立候选全部通过后提交；真实历史fixture保持原样，能检查恢复后的未来。

统一请求目前也只是有限门面。未来应持续区分：提出意图→接收者能否理解/是否愿意→是否有身体/资源/权利→原规则执行→按当事人所知反馈。脚本补全和未来语言模型使用同一入口，不能让AI直接修改事实，也不能让后台可行性检查泄漏陌生人的隐藏能力。

## 5. 近远区与性能应补的验收

先保留现有唯一时钟和稳定ID。近处关注位置、接触与短动作；远处保留目的、资源预约、在途事件及下一决策边界，稳定连续过程可批算。显示是否加载不决定人物是否存在。进入/离开区域应是执行精度的交接，不是重新生成一批居民。

必须不丢的是具名身份、唯一实物、数量、伤势/责任、未完成过程和信息来源；未被观察的微小路径可以以后另定近似合同。当前同未来逐字节验证是有价值的回归证据，但不能要求未来所有抽象演算无限展开成完全相同的逐帧细节，否则远区节省计算的目标会失效。

恢复开发后先建立分档基准：当前双聚落；同规则增加居民/工位；再增加地区及数十日/跨年推进。分别记录模拟耗时、可见帧、寻路、存读耗时、历史与文件增长；正常、资源短缺、封路和多人争用都要测。目标人口和容量仍按长期方案逐档验，不从小样本外推。

当前48视图人物CPU目标未达、九层纹理解码占用尚未降低，声音和间歇呈现问题未结案。它们是已知出口限制；本轮没有修改呈现设置或用户设备，也没有用更高帧率上限证明未来规模达标。

## 6. 恢复开发时的建议次序

下面是待讨论建议，不是新Goal或已经开始的工作。

1. **先选一个共同局面，收拢必要接缝。** 例如关键供给受阻，玩家可以劳动、交易、改造环境或协作；原身体占用和阶段依赖整理只做到支撑该局面。不先造全部通用框架。
2. **让NPC同样面对局面。** 缺工、缺预算或封路时改做、求助、缩产或失败；玩家离开再归来能看到过程结果和其可获知的依据，不全靠玩家触发每件事。
3. **让学习和社会结构产生持久后果。** 学会一种新办法，实际改变供给或解决冲突；再把一个有限职位更替/旧承诺处理接进世界，出现“礼貌仍在、利益改变”的差异。它比继续增加孤立环境计数更接近本作特色。
4. **补一次有代价但能继续的失败。** 一起事故/冲突允许撤退、丢失物资、求医及代办；关键人物失能后基本生活有替代路，再逐步扩到完整战斗、死亡和转生。
5. **用正常输入完成首小时，做独立Windows包。** 验证玩家能发现两种以上做法，知道拒绝原因、行动进展和后续选择；不能用自动推进、内部探针或堆重复劳动代替实际体验。

五行/风水、全物种、完整工法网络、多区战争和世代仍是长期目标，无需全部成为首小时的前置。正式美术继续后置。

本次最需要修正的开发倾向，是大量可靠的小包与存读核验持续增长，而完整体验迟迟未验收。后续应把“产生了什么玩家可感知的选择/后果”与规则测试一起作为完成条件；不再以新增模块、文档、按钮或断言数代表游戏向前了多少。
