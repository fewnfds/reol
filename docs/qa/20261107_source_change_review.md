# 单次来源变更成本复核

2026-11-07，用户要求对照成熟项目，核对普通生成/落地约0.22秒是否因计算或架构冗余。本次仅调研、静态核查与一轮短时分段测量，未改生产算法、数据、存档或游戏规则，未启动新Goal或完整回归。受检根main `fa075fe00329929df299e135be981414a572f347`，其游戏代码与已验6137481相同。

## 可确认的冗余

1. **受影响范围放大。** [来源候选](../../scripts/sim/environment_field_cache.gd)的`begin_source_change/step_source_change/_step_source_candidate`把源覆盖碰到的16×16块整块重算，逐格逐七通道搜索来源。两个实测落点在块交界，均重建4块、1024格。半径4核只在距离小于4处非零，单源最多45格；约22.8倍是处理范围比，不能宣称优化必提速22.8倍。有效基础缓存上，局部外圈本可复用。
2. **不变通道仍做响应准备。** [source_change](../../scripts/sim/environment_source_change.gd)对整块每格编译冷热和五行，石板/木料的冷热来源值都为0，却仍重设温度响应；已有其他来源目标或max赢家未变时也未跳过。这是可减少的计算，而非削弱世界表现。
3. **重复投影和分配。** 准备输入先调用温度/五行`actual_at`，成功值不用，bulk又按同一时刻计算一次。五行各通道共享时间/tau，仍各自求相同因子。块候选还复制输入列、已改块；begin浅复制所有已跟踪块/边界字典。两次基准都在游戏时间0，不能声称重复指数计算是此次主因。
4. **小修改带全局尾巴。** [来源参与者](../../scripts/sim/world_environment_source_participant.gd)的`affected_chunks()`取全部曾触及块并排序，[普通场](../../scripts/sim/world_environment_fields.gd)每次完成都重新合入，包括不改变场的操作。应考虑只传新增/此次触及集合，历史残留仍留原所有者。
5. **分片接口被同步跑完。** 原参与者在单个调用循环`step`直到候选完成，使全部CPU成本落到主线程同一帧。这解释卡顿如何暴露，但单纯分帧不会减少总CPU；现有分片已存在，不能包装为新发明。

## 成功项目的一手做法

- [Factorio FFF324](https://www.factorio.com/blog/post/fff-324)：将少见条件的逐tick检查换事件通知；热管更新集中到专用管理器，减少内存访问，热流算法不改。可借鉴“只在依赖变时做事”，不能直接用其每tick数字与本项目单次变更比较。
- [Factorio FFF421](https://www.factorio.com/blog/post/fff-421)：无任务机器人站休眠；重叠雷达覆盖统一按chunk注册，避免每源重复更新相同区域。其电网多线程实验也展示带宽/依赖可令并行无收益。覆盖计数不等于Reol距离衰减max，不照搬为叠加公式。
- CDDA固定源码的[add_item](https://github.com/CleverRaven/Cataclysm-DDA/blob/06be12f9884d82d387cb6b38dc549eca71c3835a/src/map.cpp#L6138-L6146)、[i_rem](https://github.com/CleverRaven/Cataclysm-DDA/blob/06be12f9884d82d387cb6b38dc549eca71c3835a/src/map.cpp#L5791-L5806)：物品变更仅对其实际发光效应使光照缓存失效；[透明度缓存](https://github.com/CleverRaven/Cataclysm-DDA/blob/06be12f9884d82d387cb6b38dc549eca71c3835a/src/lightmap.cpp#L188-L291)按脏子地图重建，无脏即退出。其lightmap本身也有整层脏标记，不宣称全部光照完全局部。Reol普通物品均有五行，适用启发是按改变通道失效，不能把它们全部当无源物品跳过。
- [Mindustry Pathfinder](https://github.com/Anuken/Mindustry/blob/3193fd81681476f3fa08bbcf3d7efb89e67229bd/core/src/mindustry/ai/Pathfinder.java#L303-L341)：先更新地块可通行输入，再标刷新；[update](https://github.com/Anuken/Mindustry/blob/3193fd81681476f3fa08bbcf3d7efb89e67229bd/core/src/mindustry/ai/Pathfinder.java#L188-L213)在间隔中合并刷新，后台预算处理，使用最近完整流场并检查当前可通行性。100ms是节流而非完成期限；策略导航允许滞后不证明Reol实际温度后果能任意滞后。

以上都支持“少算、按依赖更新、合并重复区域”，不能推导所有成熟游戏都没有事务或失败边界。

## 建议顺序（候选，尚未实施）

第一包只做**局部基础场增量更新与不变目标跳过**，不加新平台：

1. 有效缓存上，新增源直接把实际覆盖格/非零通道的贡献与旧最大值取max；旧最大值没变则不标响应重算。来源删改/移动时，只有旧源可能贡献最大值的格/通道重新查询本地来源；处理并列最大与次强接替。缺失或已脏缓存保留正确的全量回退。
2. 内存仍按chunk组织，更新范围用局部矩形/位掩码，避免把存储单位当计算最小单位。温度目标未变时不重算温度；五行只更新确有变化通道。先核对原重锚/量化规则：当前来源事件有anchor量化，跳过无变化后必须保持规定误差、共同时间和存读未来一致，不能只删除断言或改变强度规则。
3. 复用一次已检查的当前值与五行共享因子，减少字典/列复制；首次收益先以同两个普通调用复测，不扩大到极限世界压测。

只有这包之后仍超帧预算，再考虑同一模拟时刻的dirty集合去重与已有step分帧；不能跨有实际后果的事件合并，不能改成温度瞬时跳变或冻结远区。若分帧需要新异步入口，独立下一包，不混入一次算法修正。

**工程取舍：** 存读/外来定义保留完整验证；内部已验证数据在单线程受控调用内用类型、原引用和版本即可，不做全世界复制/JSON往返/完整历史重演来证明一次地面操作。局部暂存和最后一起发布本身便宜且能避免复制物品、半提交，不因“不是银行”而移除。显式can_commit链可简化阅读，但目前不是性能优先级。GPU/多线程不是本包首选；先删除上述确证无效工作。

本轮结论：**有明显过度计算，尚无证据指向引擎上限或世界法则过高。** 不承诺具体倍数；下一包通过实际耗时、访问格/通道数、原物与残留/删除次强/进行中恢复的必要定向验证决定保留或停止，不重新磨单个道具玩法。
