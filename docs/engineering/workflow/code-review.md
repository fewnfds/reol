# 提交、Codex审查与CI

依据[桌面审查](https://developers.openai.com/codex/app/review)、[GitHub集成](https://developers.openai.com/codex/integrations/github)、[官方Action](https://developers.openai.com/codex/github-action)及[计费说明](https://developers.openai.com/codex/pricing)；使用前按当前客户端核对命令和模型配置。

**账户与路由约束**：用户使用公司路由API，GPT订阅只有免费额度。采用本地原生审查，沿用本机的`custom` provider；不依赖GPT订阅，不启用GitHub云端审查或额外付费模型Action。当前明确选择`gpt-6.1-sol`作为项目审查模型，不改主模型、子代理模型、provider或权限。官方[配置说明](https://developers.openai.com/codex/config-advanced)支持自定义路由，[配置参考](https://developers.openai.com/codex/config-reference)说明`review_model`用于原生审查；实际请求仍需与非敏感配置/运行记录核对，不能只凭模型名称保证计费线路。

项目配置在本机`.codex/config.toml`的根级设置，文件已被Git忽略；配置生成器保留它，并支持重建和只读核对：

```powershell
python tools/setup_codex.py --review-model gpt-6.1-sol
python tools/setup_codex.py --check --review-model gpt-6.1-sol
```

两个命令不改变全局模型/路由。新启动的原生CLI审查读取该设置；已打开的桌面会话若仍显示旧审查模型，重新加载项目/启动新会话后再核对。用户授权的另一选项`gpt-6.1-terra`也可用同一参数明确切换，不对二者做未经实测的优劣排名。

## 采用的流程

每个可解释的工作包：开发与定向验证 → 准备提交时集中检查已推送相关SHA的CI → 定位并修复已完成的相关失败 → Git提交 → 一次原生Codex审查 → 修复有效问题并推送 → 记录受检版本及待验项。推送触发现有CI，但不因此等待；未完成的run留到下次准备提交时再检查。以具体提交及代码差异为审查对象，不以聊天历史为唯一依据。文档小改仅检查结构、链接及差异，不启动模型审查或完整Godot回归。

**触发方式**：由主代理在完成代码工作包后调用一次原生命令；原生`/review`和`review_model`设置都不是Git提交钩子。用户手工执行任意`git commit`不会自动弹出聊天。本流程不使用post-commit hook、后台常驻扫描器或自动修复循环。需要检查WIP或特定提交时可以手动触发；默认跳过纯文档和备份WIP。

**验证分工**：开发主代理是唯一的验证协调者，只有开发主代理启动原生审查。审查器自行静态分析代码和已有证据，不再调用`codex review`、子代理或其他模型审查，也不启动引擎、import/test/check、CI查询或等待器；需要复现时输出具体条件、建议命令和缺少的证据，由主代理决定一次定向验证或完整回归。已经启动的验证接续同一活进程/handle读取终态，不因为审查器看不到过程输出就另跑一次。具体PID/handle只在HANDOFF维护。

**本地长验证的完成接续**：测试进程由已有runner负责等待退出、保留完整日志和超时/错误门禁；模型不另开定时读日志、数PASS或重复报组数的循环。优先采用宿主可用的完成事件；当前工具若只提供终端session，保留同一handle，由工具层使用较长的原生等待窗口取得终态，可在代码编排层续接等待，避免每个空窗口都重新唤起模型。只在完成/失败/超时或需用户处理时报告；用户问进度、真实异常停滞或诊断错误时才读过程日志。不能因看不到即时输出重启同一回归，不派等待子代理，也不为了此功能启动另一轮Codex/API调用或定时automation。CI仍遵循下文的提交检查点规则。

官方[App Server进程事件](https://developers.openai.com/codex/app-server)提供`process/exited`（实验接口），但文档存在不表示当前聊天已暴露该能力；[后台hooks](https://developers.openai.com/codex/hooks)的输出在下一安全点/用户回合交付，hook完成不会自行开启新回合。因此文件落盘、系统弹窗或PostToolUse不能冒充已验证的“测试完成→唤醒本聊天”；未接通宿主事件时如实使用会话等待，不增加一套假回调桥。

审查意外中断时保留已有证据，恢复同一主审查会话并显式固定`model`和`provider`；中断且没有最终结论不算审查通过。

- 开发期间仍使用任务说明、AGENTS和按需技能。子代理用于可并行实现或明确专项调查，这也是Codex支持的工作方式。
- 普通代码包默认用原生审查作为主要审查。需要独立的存档、时间、空间或性能审计时，才派一个有明确范围的专项代理；不让多个审查者重复读同一整包，不每次小修改重跑整轮审查。
- 审查发现先核实触发条件、代码路径和影响，再决定修复；无实质发现即可结束。审查无发现不代表测试通过，CI成功也不代表世界规则或画面正确。
- 默认只报告能说明实际后果的问题，机械检查交给现有工具。代码审查规则见根目录[AGENTS.md](../../../AGENTS.md)的`Code Review Rules`，不另造第二套长期提示词。
- 修复会生成新SHA。保留旧审查记录，只补查改动及受影响路径；CI证据必须对应最终提交，不能沿用修复前的绿色结果。

## 现成的审查入口

| 入口 | 使用方式 | 适用场景 |
|---|---|---|
| 桌面原生审查 | 在Codex输入框输入`/review`，选择未提交改动或基准分支；结果可在差异面板查看 | 本地工作包，已有Git仓库即可 |
| CLI原生审查 | 以下`codex review`命令，输出有优先级的问题，不主动修改工作区 | 精确到一次提交，适合当前分支历史较长的情况 |
| GitHub原生PR审查 | 将仓库连接到Codex，在Codex设置中启用仓库审查；PR评论`@codex review`，或按所选事件自动触发 | 云端PR审查和留存反馈；当前官方说明默认聚焦P0/P1 |
| 桌面Code Review插件 | 连接源码账户，打开PR链接，查看描述、差异、评论和checks，选择`Review with Codex` | 在应用里查看PR及CI、调查失败；聊天审查不自动发布或合并 |
| 官方`openai/codex-action` | GitHub Actions中调用Codex，使用API密钥和受限权限 | 将模型任务纳入可重复CI；本项目暂不采用 |

CLI命令（在项目目录执行，使用前以本机帮助核对，选择一种）：

```powershell
codex review --uncommitted
codex -c model='"gpt-6.1-sol"' review --commit <完整提交SHA>
codex review --base <明确基准分支>
```

无人值守CLI命令同时显式选择`model`，避免客户端启动模型与`review_model`展示/适用入口不同造成误判；参数只对该进程生效，不改全局开发模型。

`--uncommitted`包含已暂存、未暂存和未跟踪文件。工作区混有半成品时，优先审查已隔离提交，避免把全部草稿带入。`--base`审查分支自共同祖先起的差异，不是只看最后一包。审查期间停止修改其目标；修复另开步骤。

桌面`/review`与PR插件是两个入口；侧栏安装插件不等于已启用GitHub云端自动审查，`gh`登录也不能证明Codex仓库连接已经完成。项目未采用自动云端审查、机器人评论或额外付费Action。

## GitHub与CI怎样配合

CI负责执行确定性的检查和测试；Codex负责理解差异、找行为与架构问题。两者结果都可在PR上查看，审查不替代CI或分支保护。当前仓库只有CI，没有自动发布、导出发行包或部署的CD。

现行[workflow](../../../.github/workflows/ci.yml)同时监听`push`和`pull_request`：同仓库分支建立PR后，再推送可能触发两次完整回归。两个run可能分别测试分支提交和PR合并结果；现有按`github.ref`分组的并发设置不能可靠去重，也不能把两种SHA混作同一证据。

如需引入PR，先分阶段评估；改变流程前保留现有触发器：

1. 当前仍按工作包提交、精确提交原生审查、分支推送CI，维持现有覆盖。
2. 核对当前分支与基线，必要时先整理历史集成基线，再采用小PR；不能把长期积累的历史包装成单个小功能，也不自动合并或改写历史。实时分支审计见[分支状态](../../status/branches.md)。
3. 正式采用PR流程时，将重型CI改为PR更新、默认分支推送及手动触发；未建PR的中间提交只跑定向检查，需要完整证据时手动触发一次。改触发器与建立PR流程同包交付，避免分支失去验证。
4. 若后来要求PR必需检查，先处理纯文档PR：现在`paths-ignore`会使整个workflow不运行。应始终给出轻量检查状态，再按改动选择重型Godot工作；不能直接把会跳过的检查设成必需项。

**当前不采用GitHub云端模型审查**。原生GitHub集成走Codex账号可用额度，不能假定能转到公司的模型路由；免费额度不适合作为持续审查基础。以后用户更换条件时，才考虑手动每包一次或合适的`Review trigger`。Action要求API认证并执行模型任务，API计费与订阅使用分开；官方Action示例也不能直接证明兼容公司网关，不在没有验证的情况下部署。

用户当前**无需开启Codex云端仓库审查**。GitHub只运行现有Godot/Python检查，本地Codex通过公司路由审查差异、读取CI结果。一般GitHub Actions计算时间/配额与模型tokens是两回事；不调用模型的测试不消耗模型tokens。本项目已有`gh`和CI，不为查看同一仓库再安装一套GitHub MCP。

审查本身仍是模型工作：差异、相关代码、工具结果及推理都会消耗tokens，没有可信的固定“每个PR用量”。用一个工作包、精确提交和一个主要审查者控制范围；不把全仓每次重读、每次推送审查或CI轮询当常规操作。需要无人值守时，优先评估本机事件驱动地调用原生CLI并沿用公司路由，不先增加云端订阅依赖或长期轮询器。

## CI检查和验收

现行[workflow](../../../.github/workflows/ci.yml)保留按workflow/ref分组，将`cancel-in-progress`设为false：连续推送不再取消已经运行的全量回归。GitHub默认只保留同组最新一个pending run，旧pending会由GitHub替换；这不是主代理主动取消，也不保证每个中间SHA都执行。这样在开发继续提交时仍能形成完整受检基线，下一待跑版本接近最新提交，不累计全部历史包排队。不改变push/PR触发范围或为等待增设轮询。行为依据[GitHub官方并发说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)；实际完成仍须按具体SHA/run核验，配置本身不是通过证据。

主代理维护已推送、与当前工作相关且尚待核验的完整SHA及已知run。在每次**准备提交**时集中检查一次这些目标：run已完成且失败，读取相关失败日志，定位首个真实错误并按影响修复；排队、运行中、尚未发现run或查询失败，记录待验，留待下一次准备提交。修复产生新SHA后仍须检查该新版本的证据。推送后不立即循环发现run或反复查状态；未成功推送的提交没有可归属的推送CI，按实际状态记录。

不派子代理等待CI，不开后台`tools/ci.py wait`，也不让模型充当计时器。此前允许的五分钟主动查询/后台等待方式已废止：`tools/ci.py`现有的共享锁、缓存和同run至少300秒限频只是工具安全底线，不是检查日程；遇到限频或缓存中的非终态也不绕开，直接留待下一次提交检查。没有新的检查点时不为获取结果制造空提交或让模型持续等待。

按实际受检的完整SHA和run记录结果；PR流程启用后分别登记head SHA、实际受检的合并SHA及审查版本。缓存必须区分既有结果与本次新查到的终态；排队中、未发现、查询失败、旧SHA绿色和机器人点赞均不算目标版本通过。末包结束时若尚无终态，明确记录**待验**；要求对应CI的最终验收未核到通过结果前，不能宣称已通过。涉及画面、音效、手感和声明规模的性能仍需要本机实际观察/测量。

脚本输出和缓存不会自行插入Codex聊天；当前没有GitHub完成事件到Codex消息入口的回调，不宣称它可以自动唤醒已结束的对话。原生模型审查仍是每个普通代码包一次，与CI检查各自独立，审查产出后立即结束。

这套流程不需要常驻的第二个Codex进程、自动修复循环或新增依赖。以后如果人工触发审查成为稳定瓶颈，再评估官方Action；届时固定Action/CLI版本，限制触发者和权限，审查输出与自动写回分开，不让公共PR内容取得密钥。
