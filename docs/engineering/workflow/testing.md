# 开发循环

默认路线是“明确结果 → 定位实现 → 修改 → 验证 → review/交付”。步骤可合并，无需逐步产出文件或宣读准备过程。

1. **明确结果**：确定本次要改变的可观察行为；多阶段任务在[主计划](../../plans/foundation-priorities.md)接续。
2. **定位实现**：从相关代码、调用方或错误入手，只补影响判断的缺失信息。
3. **修改**：沿现有状态归属实现，按实际需要重构和复用Godot能力；旁支想法留待选题。
4. **验证**：规则用相关短检查，交互/画面实际观察，文档核事实和链接；出现失败或明确风险再扩大范围。
5. **review / 交付**：检查正确性、成本和职责，更新受影响说明，提交并报告结果与未验证范围。推送/合并按用户授权执行。

## 性能回归

目的是回答“本次功能增加多少成本、还能否接受”，不是每次重测精确人口极限。

从[已接受历史样本](../../status/performance.json)的同人数、同场景开始；每个倍率最多3个真实窗口，正常只测1次，有异常才同负载复核或粗略降档。只测与改动有关的倍率，不强制每个改动覆盖五档。时长沿历史样本，避免把不同时段的工作量直接当纯算法差异。

同时看实际世界流速、帧时、步均、主线程/GPU耗时与有效活动量。用同条件成本差和可玩余量权衡收益；工具的退化提示是审查线索，不是自动否决规则。负载或硬件/窗口不同就标注不可直接比较，不输出伪精确百分比。新结果不自动覆盖已接受基线。

## 验证与等待

检查组成见[tests](../../../tests/README.md)，命令见[usage](../tooling/usage.md)。规则短检查约十秒；Python工具用对应短检查。旧CI和全玩法长回归已退役。

真实图形测量串行，避免互相争用设备；运行期间做独立工作，只剩等待就等待同一进程完成。仅有结果、错误或需要用户介入时再汇报测量进展。
