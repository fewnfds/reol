# 开发循环

默认路线是“接手 → 定范围 → 实现 → 短验证 → review → 交付”。小修改可以合并步骤，不要求每步创建文件或跑同一套检查。

1. **接手**：以最新用户目标和Git状态为起点。缺上下文才读[HANDOFF](../../status/handoff.md)，再用[文档地图](../../README.md)找到本次领域。
2. **定范围**：确认原状态由谁维护、要改变的可观察行为及本次结束条件。需要分阶段时改[现有主计划](../../plans/foundation-priorities.md)，算法属于所属领域内部工作。
3. **实现**：修改原入口，复用适合的Godot能力和已有接缝；有实际公共责任再抽取。难题可用本机顾问拓展思路，结论仍由代码和测量决定。
4. **短验证**：选本次可能破坏的行为或失败路径。规则改动用相关短smoke，交互/画面改动实际观察，纯文档只核事实和链接；新资源不可见时才import。只有需要独立分发或release测量才重新导出。
5. **Review**：检查变更的正确性、成本和职责；顺手核对受影响文档是否仍与代码相符，移除中间态和重复说明。无需每轮重读整个仓库。
6. **交付**：提交本次代码与必要文档，按用户授权推送/合并。报告行为、验证和未完成范围。接续页覆盖成实际停点，事实更新原页；完成的任务不留在待办中。

## 性能回归

目的是回答“本次功能增加多少成本、还能否接受”，不是每次重测精确人口极限。

从[已接受历史样本](../../status/performance.json)的同人数、同场景开始；每个倍率最多3个真实窗口，正常只测1次，有异常才同负载复核或粗略降档。只测与改动有关的倍率，不强制每个改动覆盖五档。时长沿历史样本，避免把不同时段的工作量直接当纯算法差异。

同时看实际世界流速、帧时、步均、主线程/GPU耗时与有效活动量。用同条件成本差和可玩余量权衡收益；工具的退化提示是审查线索，不是自动否决规则。负载或硬件/窗口不同就标注不可直接比较，不输出伪精确百分比。新结果不自动覆盖已接受基线。

## 验证与等待

规则短检查当前约十秒；组成查[tests](../../../tests/README.md)，命令查[usage](../tooling/usage.md)。Python工具改动只跑相应工具短检查；链接与入口可用现有结构工具辅助。出现真实失败再扩大排查，不恢复旧CI、分片矩阵或全玩法长回归。

真实图形测量串行，避免互相争用设备；运行期间做独立工作，只剩等待就等待同一进程完成。仅有结果、错误或需要用户介入时再汇报测量进展。
