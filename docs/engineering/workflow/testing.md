# 开发循环

唯一默认路线是“接手 → 定义出口 → 实现 → 相关验证 → review/交付”。小修改可以合并步骤；不为流程本身创建计划、日志或报告。

1. **接手**：以最新用户目标和Git状态为起点。缺上下文才读[HANDOFF](../../status/handoff.md)，再用[文档地图](../../README.md)找到本次唯一相关领域。不要先通读整个仓库。
2. **定义出口**：把任务收敛成一个可观察结果、验收条件和明确不做项，按 issue 的方式指出入口/组件。只有跨多个阶段或需要长期接续时才改[主计划](../../plans/foundation-priorities.md)；一次性想法留在对话或本机工作区。
3. **实现**：修改现有owner和入口，复用Godot能力与既有接缝；只有出现真实公共责任才抽取新模块。旁支想法不自动扩大本次范围，研究结论标成候选，最终以代码和测量为准。
4. **相关验证**：选择本次最可能破坏的最小检查。规则改动用相关短smoke，交互/画面改动实际观察，纯文档核事实和链接；真实失败才扩大排查，新资源不可见时才import。性能只在功能确实影响运行成本时做历史同负载对照。
5. **review / 交付**：检查行为、成本、职责和变更文档，删除本次发现的重复或中间态；更新唯一事实页，只有停点或未完成事项改变才覆盖[HANDOFF](../../status/handoff.md)。提交并报告改变、验证、未验证范围；是否推送/合并按用户指令执行。

## 性能回归

目的是回答“本次功能增加多少成本、还能否接受”，不是每次重测精确人口极限。

从[已接受历史样本](../../status/performance.json)的同人数、同场景开始；每个倍率最多3个真实窗口，正常只测1次，有异常才同负载复核或粗略降档。只测与改动有关的倍率，不强制每个改动覆盖五档。时长沿历史样本，避免把不同时段的工作量直接当纯算法差异。

同时看实际世界流速、帧时、步均、主线程/GPU耗时与有效活动量。用同条件成本差和可玩余量权衡收益；工具的退化提示是审查线索，不是自动否决规则。负载或硬件/窗口不同就标注不可直接比较，不输出伪精确百分比。新结果不自动覆盖已接受基线。

## 验证与等待

规则短检查当前约十秒；组成查[tests](../../../tests/README.md)，命令查[usage](../tooling/usage.md)。Python工具改动只跑相应工具短检查；链接与入口可用现有结构工具辅助。出现真实失败再扩大排查，不恢复旧CI、分片矩阵或全玩法长回归。

真实图形测量串行，避免互相争用设备；运行期间做独立工作，只剩等待就等待同一进程完成。仅有结果、错误或需要用户介入时再汇报测量进展。

## 收尾记录

只有会改变未来实现、复现、恢复或验收的事实才写入仓库。代码/文档已经自解释的内容不再复制到状态、计划和总结。临时排错、顾问原文、完整命令输出留在本机日志或Git历史；需要长期保留的结论回到它唯一的主题页。
