# 模拟系统的复杂度与扩展范式

本页规定新增或扩展模拟能力时怎样控制组合成本，并记录当前源码的访问形状。它不是另一个执行后端，也不是已完成的优化清单。当前跨步观察、后台个人规划已经在使用；本次审查提出的索引、投影及调度数据结构整改尚未实施。施工顺序归[主计划](../plans/foundation-priorities.md#系统组合成本审查)，实测条件与数字归[BASELINE](../status/baseline.md#系统组合成本测量)。

## 成本为何会随系统装配放大

系统数量本身不是复杂度阶数。新增能力若只处理它实际拥有的少量实例，成本可以主要随有效活动增长；若把它的全量数据塞入每人的通用查询，或在每个共同时间子区间扫描全部实例，就会抬高其他系统的成本。

审查至少区分以下规模：`N`身体数、`U`外步内共同时间子区间数、`W`待唤醒主体、`Q`待算项、`S`服务设施、`A`任命、`E`状态实例、`K`单人认识、`L`局部候选、`D`候选作业落点、`B`实际复制的字节/嵌套内容。它们不能都简写成“人数”。

例如，站位请求率随人数增长，每个请求检查D个落点，每个落点又遍历N人，成本就是`请求率 × D × N`；在请求率也随N增长的条件下才出现近似平方增长。普通观察即使每次只服务4个目标，若每个目标仍重建大视图、扫描满K条认识、查全组织，有限片数也不代表有限低成本。

判断一次扩展的端到端成本，包含**写入及失效维护、入队/选取、输入准备、实际计算、采用复核、通知扇出、快照发布与显示消费**。CPU累计时间和阻塞世界推进的挂钟时间分别解释，父子计时不能相加。缓存命中率、局部密度、输出大小和队列等待同样属于成本。

## 新能力怎样接入

### 先约定访问范围，再选择执行设备

| 数据/工作特征 | 优先方式 | 必须说明的边界 |
|---|---|---|
| 全员共同热数据，确实每步需要 | 继续Packed页的顺序批处理 | 一次批合并多个需要，避免每个系统再遍历全员；低成本线性扫描可以保留 |
| 稀疏活动或只有变化者需要 | 原owner维护活跃/脏集合 | 唤醒、满值休眠、取消、删除和恢复入口完整；不为每单位挂独立Node/Timer |
| 已知未来到期 | 原领域保存到期事实，派生到期索引/队列 | 软事务不切碎全部身体；堆/桶选择按时间分辨率和分布，过期节点清理与内存也有预算 |
| 某人/目标/范围的关联查询 | 按actor/target/组织/空间的派生索引 | 查询结果本来有r项时至少需O(r)；不能用一个“大组织桶”冒充与规模无关 |
| 重复读、少量改的描述 | 窄投影、版本比较、按需构造不可变版本 | 写入/失效及内存保留一起计费，冷读可直接算；不为每个字段构造缓存框架 |
| 昂贵、纯读、结果可迟到 | 脱离输入的有限WorkerThreadPool任务 | 准备/复制/回收/复核算全账；保持旧承诺，当前owner决定采用，不共享可变World |
| 表现数据 | 可见范围、相关修订、Godot批绘/Shader | 伤害、预约和物品后果不能由画面推算代替；画面旧值不阻塞世界 |

事件驱动也有成本：`变化次数 × 订阅者数`可能比一次顺序批更贵。只有相关人被唤醒；同actor同原因合并，延迟review不提前触发重规划。对于确需周期采样的连续变化保留错峰/积分/阈值，而不是广播每一次微小数值变化。

### 窄投影与不可变认识

`operation_actor`、`operation_target`和`_self_view`当前是组合读入口，不是所有新能力必须无条件塞字段的容器。规划、准入、最终提交、UI各自只取必要字段；同一个owner阶段内复用已构造上下文。阶段之间发生过写入时只按相关版本刷新，不能把后台输入直接当作完成时的当前事实，也不能向提交后的review继续传提交前的旧状态。

公共目标描述可以按目标/投影种类/相关版本共享。先核是否有资格进行这次观察，再比较版本、取得内容；角色自己的来源、观察时间、缺席、失效、教导线索和渠道版本仍是私有证据。发布过的旧版本不原地改，未再观察的人继续持旧内容；带观察者权限的字段不能混进无条件共享的公共快照。删除及目标身份复用、旧版本释放、存读时的结构均须明确。

共享快照命中不等于某个观察者已经知道。乙首次取得甲早已生成的公共版本，仍是乙的新认识，应正常更新乙的个人revision与知识唤醒；只有相对乙已有记录确实未变，才能跳过内容改写。快路径不能跳过guest的独立可见性观察或来源/时间元信息。

只给“目标版本”加一个整数还不够：版本必须覆盖该投影实际读取的库存、阶段、可见状态等写入口；不同消费者不共用含义模糊的全局脏标。光学遮挡、静物外观、库存/进度、个人目的和UI详情可以有不同失效范围。先拆当前可证实的过宽依赖，再决定是否需要细到地块的增量框架。

### 索引与调度仍由原owner负责

身体当前点、已受理目的地、设施预约是三种含义。站位索引从原事实派生，身体移动、目的地改变、行动取消、死亡/换槽、同批准入及片内时刻都要覆盖；不能只复用一份上帧战斗桶，或另建持久占位真值。占位过滤活体，普通观察还需要可见尸体等候选，不能把消费者不同的过滤条件固化进一个漏项的共享桶。稠密桶查到很多候选时完整过滤，必要时分片等待，不丢结果。

普通观察同样消费身体空间查询；当前`Knowledge.service`在战斗桶不存在时有全员回退。C05收窄战斗索引之前，先为这些消费者明确候选覆盖与几何时间有效性，不能简单删去兜底。`before_motion`捕获的旧位置也被`World.position_at`用于片内工作结算/站位，不只服务战斗；减少复制须覆盖全部读者，不能按函数名判断无用。

调度要分“未来未到期”和“现在可服务”，选一项不应反复遍历全部未来事务。可用按域的就绪集合、按优先级/年龄的结构及到期索引，但必须保现有同主体合并、原首次等待时间、年龄公平、跨域机会、片内次数限制、完成独立回收和容量拒绝后的领域重试。堆的惰性取消也会积累无效节点；需要可计数的清理/重建路径，不能把无界清理藏进peek。

领域保存的`life_pending`等欠办凭证也不等于一个需要每子区间重复触发的闹钟。入队、在途、依赖等待、容量拒绝后待重试分别有明确接续入口；保留事实以便恢复，不通过反复扫描/合并已存在队列项来维持它。新的独立刺激仍由领域保留，不能因为已有后台任务就清掉。

## 每次框架扩展的成本说明

对新领域或改变访问形状的扩展，在原主题说明中回答下列问题即可；一个新的技能/配方数据实例不必另建表格或独立性能测试。

| 内容 | 需要回答的问题 |
|---|---|
| 状态及入口 | 谁写事实？哪些变化/到期让它有工作？无实例/满值/无变化时还做什么？ |
| 数据范围 | 读写哪些字段？规模取决于总人数、局部密度、个人关联还是全目录？被上层每人/每目标/每子区间调用后总共访问多少项？ |
| 派生数据 | 哪个owner维护索引/版本？创建、修改、撤销、死亡、槽位变化、加载怎样失效/重建？内存增长和首次冷读成本如何？ |
| 时间与采用 | 哪些结果必须当前有序成立？哪些允许迟到？等待时继续什么？提交时核哪些事实，不以陈旧结果覆盖新承诺？ |
| 放大与退路 | 同时到期、密集候选、队列积压、批次数/内容目录增长时会怎样？时间预算之外的单片是否还可能很重？ |
| 可观察证据 | 记录触发/合并、访问候选、快照构造/字节、命中/失效、队列等待/未完成及有效活动中的哪些指标，才能判定省算而非停工？ |

实现先沿已有World、领域owner、Deferred、Resource编译和Frame扩展。共享的是这些计算与数据访问约定，不引入万能事件解释器、每域线程池、全事实广播、另一套ECS或第二份世界。

## 怎样验证而不追逐人数极限

沿[开发循环](workflow/testing.md)选择相关短检查。算法归因用单参数微核或受控短窗；产品性能用同源码、场景/成熟度、硬件、倍率、频率、画面及后台设置的release窗口，不能把workers0的无墙钟截断路径当成正常后台模式。插桩需对照未插桩，叶函数的包装时间不当作业务成本。

除了帧时/世界流速，必须看有效活动、完成/移动量、待算数量、各域等待及未完成；不以减员、无事可做或无限延后换取“性能通过”。新增无关内容是否拖慢已有查询、新增独立聚落是否提高原聚落单人查询成本、缓存是否传播到未观察者，是比盲加万人更有解释力的反例。一次短窗不证明长期排队稳定，也不证明多弹幕/全年环境上限。

### 可观察计数的最小闭环

以下是首批整改应补的诊断，不是当前都已有的字段。计数留在原owner或现有诊断投影，不做全事实事件广播；默认只累计标量/有限样本，详细字节与叶函数计时按需开启，避免诊断重新放大热路径。

| 要区分的问题 | 最小观测 |
|---|---|
| 是事务真的多，还是调度反复翻表？ | 各域新请求/合并/拒绝、未来/就绪/在途项数；take调用、实际访问项数与累计用时；有效服务片/完整任务分别计数 |
| 帧准时，NPC是否在等待？ | 各域完成吞吐、**当前仍待算项（含尚未准入队列的领域欠办）**的最老年龄及有限年龄分布；完成任务等待单独统计。现有maximum_wait在取出时才更新，永远未获服务者不能靠它被发现 |
| 是核心搜索贵，还是准备/复制贵？ | 输入准备、纯计算、回收/采用分开计时；本人/目标投影构造数、认识复制项数、候选访问数、丢弃提案及原因；不把父子计时叠加 |
| 缓存/索引是否省掉更多工作？ | 构造/命中/失效/维护、候选假阳性、当前/峰值缓存规模、退役节点清理；按需读时的冷峰也记录 |
| 算法是否只是让人停工？ | 相同合法输入下的真实操作完成、移动/交付及各类活动/正当闲暇，存活/目标机会/实际供给等负载条件一起报告 |

按短窗看积压年龄和完成率的变化，必要时接续同一状态复核“持续需求”与“一次开局突发”。被合并或尚未被服务的工作没有完整CPU用时，仅把已消耗时间除以世界时间不能得到需求率，更不能证明稳态；人少、任务少的低成本窗口也不替代真实活动窗口。世界毫秒与墙钟微秒分别计，避免把允许的模拟等待误读为主线程冻结。

## 公开依据与适用范围

- [Godot通用优化](https://docs.godotengine.org/en/4.7/tutorials/performance/general_optimization.html)和[WorkerThreadPool](https://docs.godotengine.org/en/4.7/classes/class_workerthreadpool.html)：先找算法/数据热点，小任务并行可能更慢。本项目继续用Packed列、原生批操作、私有AStarGrid、线程池及MultiMesh；游戏的读集合、失效、关联和提交语义需要自己定义。
- [Factorio FFF421](https://factorio.com/blog/post/fff-421)：闲置实体休眠、重叠覆盖用共享登记、纯读计算可并行；电网的多线程尝试也因内存吞吐限制未取得整体收益。借鉴工作集与数据依赖，不移植其数字/调度间隔。
- [Flecs查询文档](https://www.flecs.dev/flecs/Queries.html#performance-and-caching)：缓存查询在读速度、创建、内存和维护成本之间权衡。借鉴稳定查询/关联的派生缓存，不据此要求替换当前后端。
- [CDDA物品唤醒源码](https://github.com/CleverRaven/Cataclysm-DDA/blob/master/src/item_wakeup.cpp)：按到期与身份管理工作可作参考；把所有到期项一次处理完不是墙钟预算，不能直接当作本项目软服务实现。
