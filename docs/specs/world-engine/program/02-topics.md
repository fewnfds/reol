# 创作、预览与工具验收合同

工具随[顶层框架](../../../engineering/architecture/05-framework-domains.md)交付；本页保留详细候选合同，不登记当前能力或另排阶段。建设依赖见[基础建设计划](../../../plans/foundation-priorities.md)，实际接入/缺口见[技术总表](../../../status/technical-status.md)。

## 创作工具的领域覆盖

| 工具 | 能编辑或观察什么 | 第一版交付方式 |
|---|---|---|
| 定义编辑 | 地块/材质、物种身体、物品、来源/响应、可用动作的参数和引用 | 原JSON规范、校验与简易属性表；按需用Godot Inspector呈现 |
| 地图/空间编辑 | 平面地表/材质、真实结构、门顶、放置点及区域 | 少量笔刷、拖线/矩形、吸取、预览与非法原因；按需复用Godot的 `TileMapLayer`/`TileSet` |
| 对象装配 | 已支持单位/物品的模板、数量、初始状态、容器和关系 | 调色板+属性检查，保存场景装配数据，不另造模拟状态副本 |
| 环境编辑 | 地理范围、天气参数、灵物来源、材质导通/屏蔽与响应 | 曲线/参数表+可切覆盖图，能追到原来源、条件与实际消耗 |
| 模板/开局编辑 | 房屋、地点、家具、库存、人员/岗位、起始知识与有限工作安排 | 组合模板展开成真实实例并重映射内部ID；外部引用明确，不能复制独物历史 |
| 运行检查 | 开始/暂停/快进、过程/来源、物资/能量账、保存重启与性能 | 独立预览会话、最小调试面板及现有CLI测试；普通玩家界面仍受认知限制 |

优先Godot现有Inspector、TileMapLayer和少量项目自有面板；反复验证编辑负担后才增加EditorPlugin/InspectorPlugin。自有工具与第三方addons清楚分开，第三方源码不改。不先开发通用可视化脚本语言、完整节点图编辑器或新的通用引擎编辑器。

现有JSON定义/开局保持唯一可持久来源；若用Resource帮助Inspector编辑，作为明确适配视图，验证后写回同一份数据，不同时维护JSON与tres两份权威内容。不把运行伤势、余额、个人经历写回共享模板或TileSet。运行状态也不能直接指向会被编辑器修改的共享资源。

### 开发创作、预览与玩家操作

- 创作模式修改定义草稿或开局布局，提交前验证字段、引用、范围、承载和循环；可直接布置但不得破坏底层不变量，不伪造玩家劳动/付款历史。
- 预览模式从草稿创建独立候选，确定seed和规则版本后运行；默认停止时丢弃预览的运行变化，可单独保存开发快照。首版不把已经模拟过的伤势、消费与历史自动烘焙成新的开局。
- 玩家模式在实际世界中通过本人感知/能力、社会权限、材料、耗时和中断改变世界。开发工具看到全量真值不意味着玩家获知它。
- 撤销/重做只作用于编辑草稿。预览已推进时间后，用独立快照重置到基准，不能只撤掉墙却假装热扩散、NPC行动和物资消费也已倒流。
- 编辑模板不会自动更改已存在的实例或存档历史。定义ID、规则版本和开局/生成版本有清楚兼容策略；新能力从明确边界启用，支持范围内的旧档经候选转换到当前模型，不重写历史fixtures。不承诺永久运行全部历史内容/规则版本。

### 内容绑定与独立装配

工具使用[世界装配合同](01-topics.md)绑定会话实际依赖的数据定义、开局基线、地图输入和版本/摘要。预览或新世界可选择新版，原会话继续原包；规则代码另按兼容政策处理，不把数据快照等同于运行任意历史代码。

定义、开局和地图草稿均先构造独立候选，恢复不重跑开局发行，也不借活世界补人员、库存或位置。直接读盘依赖、地图规格和普通多区呈现等实际限制在技术总表集中维护；本规格不保存第二份代码进度或历史迁入承诺。

验证包括相同定义ID的两个受支持内容包、不同布局/人员的独立候选：原实例保持已声明数据，新世界采用选定版本，各自可启动和存读，失败不更改活世界。支持输入按兼容政策声明，原fixture只读。

## 内容如何建立在架构之上

以“寒光石”和山中小院为创作例子，不为它们编剧情：

1. 从已有物品模板创建新定义，选择已支持的吸热源和微光能力，填写容量、功率、消耗及材质；此时不新增专门的寒光石脚本。
2. 在空间工具中修改地表，画墙门与屋顶，摆放真实石头、火源、柜子和不同生物；保存为地点模板或开局。
3. 隔离预览观察冷热、照度、五行环境影响及受体行为，检查来源与总账；搬石入柜、开门、拆墙并比较结果。
4. 校验后作为内容进入普通新局。玩家按正常规则改造，NPC使用同一空间与环境；离开返回和重启后保持实际结果。

同类地块、物品、建筑布局和已有能力组合应主要改数据；全新身体结构、传播规律、动作语义或生命过程需补运行代码、校验和测试，之后才进入编辑器。编辑器不会凭文字生成未知规则。正式美术继续后置，代码示意图保持可读。

## 文件职责与验收

沿用现有目录：`scripts/sim/`保存规则/权威状态，`runtime/`连接输入和视图，`persistence/`处理文件与迁移，`data/definitions/`保存定义，`data/scenarios/`保存开局/装配，`tools/`保存离线校验/开发工具。若需要Godot插件入口，按官方布局放独立的项目自有插件，纯规则不移进插件；不提前创建空目录。

每个运行模块和对应小工具一起验：定义→校验→放入候选→运行→实际改造→离场→存读→恢复。至少两种内容/布局复用同一机制，并覆盖非法引用、重叠/不可达、容器成环、重复提交、多源竞争、改结构、能力不适用及旧档迁移；不以单个精调事件证明通用性。

开发观测包括事实、来源、时间、费用与失败原因；覆盖图仅是可检查投影。温度状态与五行场分别检查来源和时序，可吸收灵气由物品独立记账；光照检查来源/遮挡，行为检查请求与结果是否分开。性能按活跃单元/对象/源/路径/结构变更逐级施压，记录帧时、模拟耗时、内存和存读；不预先保证任意地图规模。

完整回归沿现有CLI/CI，精确到相应提交；CI仅在准备实际提交时集中核对，未终态留待下次，无主动轮询/后台等待/被动代理，未验范围明确登记。详见[工作流](../../../engineering/workflow/code-review.md)。纯文档只查结构、链接和差异；框架完成按约定的公共能力、实际组合和证据判断。

## 交付与进度归属

编辑与观察能力归入其服务的框架出口，跨领域预览沿公共装配/时间/存读合同验证。主计划不按某件灵物、一个画笔或单项算法排定；实现细节在已授权框架内安排，进度回到技术总表和HANDOFF。
