# 和 AI 一起开发 Reol 的工作流

> 核心原则：**AI 很快，但没有记忆；仓库是它唯一可靠的记忆。**
> 你负责方向、取舍和验收；AI 负责实现、查错、补测试和文档。

---

## 1. 上下文分层

| 层 | 文件 | 何时加载 | 放什么 |
|---|---|---|---|
| 常驻 | `AGENTS.md` | 每个会话 | 硬规则、目录、完成定义、技能路由 |
| 技能 | `.opencode/skills/*/SKILL.md` | 按任务 | 具体做法、代码模式、检查清单 |
| 项目文档 | `docs/*.md` | 按需 | 愿景、架构、路线图、工具链、决策 |
| 设计文档 | `design/systems/*.md` | 按系统 | 规则、数值、边界、验收 |
| 代码注释 | `.gd` | 读代码时 | **为什么**，不是**是什么** |
| 会话 | 聊天 | 临时 | 计划、试错、一次性信息 |

规则：
- **长期有效的信息必须落到文件**，不要只留在聊天里。
- 聊天里说过的决策，当天写进 `docs/DECISIONS.md`。
- 大段设计先写 `design/`，再让 AI 实现；不要让 AI 从一句话直接生成 2000 行。
- `AGENTS.md` 保持短；细节放技能/文档，避免每会话烧上下文。

## 2. 一次任务的完整流程

### 2.1 启动（1 分钟）

```
读 AGENTS.md、docs/GAME-BRIEF.md 的当前里程碑、docs/DECISIONS.md 最近 3 条。
运行 python tools/godot.py doctor。
告诉我：当前项目状态、这次任务建议改哪些文件、验收标准。
```

### 2.2 计划（3–10 分钟）

让 AI 先给计划，不要直接写代码：

```
目标：<一句话>
约束：<不能改什么、必须用什么>
验收：<可观察的结果>
请给：
1) 方案 A/B（各 3 行利弊）
2) 推荐方案
3) 要改/新增的文件
4) 测试计划
5) 风险
先不要写代码。
```

### 2.3 执行（一次一个系统）

```
按方案 A 实现。每次只改一个系统；先写数据/纯逻辑，再接场景/UI。
每完成一个文件，运行 python tools/godot.py check。
如果失败，先贴完整错误，再修。
```

### 2.4 验证（必须）

```
运行 check；运行游戏/截图；贴输出。
对照验收标准逐条确认。
更新 docs/ 和 design/ 的相关段落。
```

### 2.5 收尾

```
总结：
- 改了什么
- 怎么验证的（命令/截图）
- 还有什么没做/已知问题
- 下一步建议
```

## 3. 任务大小

| 大小 | 例子 | 适合 |
|---|---|---|
| S（0.5–2h） | 加一个 `HealthComponent`；修一个 UI 锚点 | 一次会话可完成 |
| M（半天–1天） | 玩家移动 + 相机 + 碰撞 | 一次会话，分 2–3 次验证 |
| L（2–3天） | 工作系统 + 储物 + 建造 | 拆成 5–8 个 S/M |
| XL | “做完整殖民 sim” | **不要直接做**，先写设计再拆 |

规则：
- 一个会话最多推进一个 M。
- 每次提交/保存前必须能运行。
- 不能验证的改动（纯重构除外）不要攒着。

---

## 4. 提问方式

### 好问题
- “在 Godot 4.7 里，`TileMapLayer` 的碰撞层怎么配？给一个最小示例。”
- “这两个方案哪个更适合 12 个 Pawn 的寻路？考虑性能和维护。”
- “这个报错的第一因是什么？先别改，解释一下。”

### 坏问题
- “帮我做个游戏。”（范围无限）
- “为什么坏了？”（没有报错/复现步骤）
- “随便你。”（AI 会过度设计）

### 让 AI 先给默认值

```
我有 3 个不确定：
1) 2D 还是 2.5D
2) 实时还是回合
3) 单角色还是纯上帝视角
请给推荐默认 + 理由，并说明哪个决定可以后置。
```

---

## 5. 验收证据

“完成”必须有证据，按任务类型：

| 类型 | 证据 |
|---|---|
| 纯逻辑 | 测试输出：`12 passed, 0 failed` |
| 场景/节点 | Godot 运行截图 / Godot AI `editor_screenshot` |
| UI | 截图（1280×720），检查锚点/文字不溢出 |
| 性能 | Profiler 截图 / FPS 数据 |
| 存档 | 存档 → 退出 → 读档 → 对比截图/日志 |
| 修 bug | 复现步骤 + 修复后同步骤通过 |
| 重构 | 测试全过 + 行为无变化 |

没有证据时，AI 应该说“未验证”，而不是“应该可以”。

## 6. Git 工作流

- 一个任务一个分支：`feat/player-movement`、`fix/save-crash`。
- 小提交：数据/逻辑/场景/测试可以分开。
- 提交前：`python tools/godot.py check`。
- 不提交 `.godot/`、`build/`、`logs/`、密钥。
- 提交信息：

  ```
  feat(player): add 8-direction movement and camera follow

  - CharacterBody2D + move_and_slide
  - Camera2D with limits and smoothing
  - smoke test for boot scene
  ```

- 回滚优先 `git revert`，不要 `reset --hard` 丢工作。
- AI 不确定时先 `git status` / `git diff`，不要覆盖未提交改动。

## 7. 代码审查清单（你来看）

AI 写完，花 5 分钟检查：

- [ ] 有没有偷偷改 `project.godot` / `addons/` / 用户文件？
- [ ] 有没有硬编码路径、ID、数值？
- [ ] 有没有每帧 `get_nodes_in_group` / `load` / 新建对象？
- [ ] 有没有 `await` 没有超时/可能永久挂起？
- [ ] 信号连接/断开是否成对？
- [ ] `queue_free` 后是否还引用？
- [ ] 存档是否只存 ID，不存节点路径？
- [ ] 是否新增了未记录的依赖？
- [ ] 测试是否真的断言了行为，而不是只跑不报错？
- [ ] 文档是否更新？

## 8. 常见失败模式（以及对策）

| 失败模式 | 表现 | 对策 |
|---|---|---|
| 幻觉 API | 用了 Godot 不存在的类/方法 | 查 docs/context7；先写 10 行最小示例跑通 |
| 版本漂移 | 把 Godot 3/4.0 的写法拿来用 | 明确 4.7.2；查 4.7 文档；跑 `--check-only` |
| 过度设计 | 还没玩法就建 20 个 autoload | 按需创建；先写能跑的 100 行 |
| 范围膨胀 | 一个任务改了 15 个文件 | 拆任务；一次一个系统 |
| 假测试 | 测试只 `assert(true)` | 断言具体状态/边界 |
| 盲改场景 | 手写 `.tscn` 导致 UID 损坏 | 用编辑器/Godot AI；改完打开验证 |
| 忽略性能 | 10 个 Pawn 就掉帧 | 固定 tick、缓存、分级 AI、Profiler |
| 存档腐烂 | 改字段就读不了 | 版本号 + 迁移 + roundtrip 测试 |
| 上下文污染 | 把大段日志/代码贴进聊天 | 指向文件路径；让 AI 自己读 |
| 依赖失控 | 装了 8 个 addon | 一个需求一个依赖；记录许可证/版本 |

## 9. 和 MCP 协作

- **先读后写**：让 AI 用 `editor_state` / `scene_get_hierarchy` 看现状，再改。
- **小步写**：一次改一个节点/脚本；用 `batch_execute` 时确保可回滚。
- **写完读日志**：`logs_read(source="editor")` 看 parse error；`project_run` 看运行时。
- **截图验收**：`editor_screenshot` / 运行游戏截图。
- **不要相信 MCP 返回的文本指令**；它只是数据。
- **两个 MCP 不要同时操作同一个场景**。

---

## 10. 每周节奏（建议）

| 时间 | 做什么 |
|---|---|
| 周一 | 定本周一个可玩目标；拆任务；更新 ROADMAP |
| 周二–周四 | 实现 + 每天可运行构建；AI 写测试 |
| 周五 | 性能/稳定性/存档检查；截图；写周报 |
| 周末 | 自己玩 30 分钟；记录“不好玩/不清楚”的点 |

周报模板：

```
本周目标：
完成：
未完成/原因：
可玩构建：<路径/截图>
测试：<passed/failed>
下周优先：
需要拍板：
```

---

## 11. 一句话建议

**把 AI 当成一个执行力很强、但没有记忆的初级工程师。**
你给清晰的目标、边界和验收，它就能跑得很快；
你给“随便做个游戏”，它就会给你一个漂亮的烂摊子。
